# Разделение работы над очередью

Предлагаемый план по текущему коду репозитория и [требованиям преподавателя](REQUIREMENTS.md). Это договорённости команды, а не новые требования заказчика. Реализация WebSocket и расписания в просмотренной рабочей копии отсутствует: их реальные интерфейсы нужно сверить с авторами до интеграции.

Обозначения: **ты** — API, допуск и интерфейс; **коллега по очереди** — механизм очереди; **автор расписания** — источники и политика расписания; **автор WebSocket** — доставка обновлений.

## 1. Основная граница

**Коллега решает, как меняется очередь. Ты решаешь, кто и через какой интерфейс может попросить её изменить.**

Коллеге отдаётся полноценный сервис очереди с хранением и тестами, а не только структура данных. Тебе не придётся повторять его проверки в HTTP-обработчиках или на фронтенде.

```text
Студенческий / преподавательский интерфейс              [ты]
          │ HTTP-команды; получение состояния
          ▼
main.py: авторизация, разбор запроса, допуск, HTTP-ошибки [ты]
          │ доверенные данные студента и лабораторной
          ▼
QueueService: порядок, состояния, операции, история     [коллега]
          ├── QueueRepository: транзакции и хранение     [коллега]
          └── SchedulePolicy: доступные занятия         [автор расписания]

После сохранённого изменения → уведомление WebSocket   [твоё подключение
                                                       к готовому транспорту]
```

Вся запись в хранилище проходит через QueueService. Ни фронтенд, ни HTTP-обработчик, ни WebSocket не переставляют записи самостоятельно.

## 3. Что именно делает коллега по очереди

### Модель

Минимальные сущности:

- `QueueSession`: ID очереди, курс, разрешённые группы, привязка к занятию/дню, времена открытия записи, конца записи и окончательного закрытия, ручной режим, версия состояния.
- `QueueEntry`: ID записи, очередь, подтверждённый GitHub-логин, группа, ФИО, канонический ключ лабы, время записи и стабильный порядковый номер, статус, время вызова и завершения, результат.
- `QueueSnapshot`: состояние очереди, ожидающие по порядку, вызванные, версия, сведения о доступности записи.

ФИО и название лабы сохраняются как данные для истории: изменение внешних данных не должно делать старые записи нечитаемыми. Для студента API формирует отдельное представление с его записью и местом; административный снимок не нужно целиком отдавать студентам.

Предлагаемые статусы записи:

```text
waiting → called → finished (defended | not_defended | absent)
waiting → withdrawn
waiting / called → expired (закрытие в конце дня)
```

Названия технические и могут быть другими. `expired` не равно «не явился»: отсутствие отмечает преподаватель, истечение дня — система. Выход уже вызванного студента предлагаем запрещать; это допущение команды, его нужно записать в PR.

### Операции и гарантии

- Запись в конец очереди и выход из неё.
- Вычисление места среди ожидающих; вызванный получает состояние «вызван», а не новое место.
- Вызов следующего ожидающего с атомарным переводом в `called`.
- Несколько `called` одновременно: завершение одной защиты не завершает остальные.
- Завершение конкретной защиты одним из трёх результатов.
- Повторная запись после завершения, в том числе «не защитил» и «не явился», в конец очереди, если запись ещё открыта.
- Запрет второй активной записи: активными считаются и `waiting`, и `called`.
- Порядок по времени записи с устойчивым разрешением совпадений времени, например серверным последовательным номером.
- Досрочное закрытие и ручное открытие записи без уничтожения уже ожидающих.
- История с датами, исходами и фильтрами по курсу/группе/дню; при необходимости пагинация.
- Обработка границ времени и перезапуска, когда приложение пропустило конец дня.

После конца пары закрывается **запись**, а не обслуживание. Ожидающие и вызванные сохраняются до конца дня. На следующую пару они не переносятся автоматически. Изменение расписания также не должно удалять существующие записи.

Коллега сам выбирает хранилище, обосновывает его в ADR и обеспечивает сохранность истории. Одного словаря в памяти для итогового решения недостаточно. SQLite допустим по ответу преподавателя, но не обязателен. Если нужны файл БД, volume или переменная окружения, их настройка и документация входят в его задачу.

Проверка дубликата, выбор следующего, смена статуса, запись истории и увеличение версии должны быть согласованы транзакционно. Два одновременных `call_next` не могут вызвать одного студента дважды. Два одновременных `join` от одного студента не могут создать две активные записи.

Ядро не импортирует FastAPI, не читает cookie, не принимает HTTP Request, не вызывает Google Sheets/GitHub и не отправляет WebSocket. Оно получает доверенные данные через контракт и возвращает результат либо предметную ошибку.

## 4. Что именно делаешь ты

### Backend-интеграция

1. Создаёшь один экземпляр QueueService с его хранилищем и SchedulePolicy; подключаешь корректный запуск и остановку периодического `reconcile`.
2. Получаешь курс по стабильному `course_id`, разрешаешь лабораторную в канонический ключ, проверяешь включение очереди для курса.
3. Устанавливаешь личность студента на сервере. Поле `github` из формы не является подтверждением личности.
4. Читаешь из таблицы группу, ФИО и результат успешной проверки лабы. Не доверяешь переданным браузером ФИО, группе и флагу `passed`.
5. Передаёшь проверенные данные в QueueService. Доступность занятия для группы и времени проверяется внутри сервиса через SchedulePolicy; браузер не назначает себе очередь произвольной группы.
6. Для выхода проверяешь владельца записи; ID чужой записи не должен давать право удалить её. Для админских действий используешь серверный `Depends(require_admin)`.
7. Переводишь предметные ошибки в HTTP и устойчивые коды для локализации.
8. Формируешь разные DTO для студента и преподавателя. Студенту достаточно своей записи, места и состояния доступности; список ФИО всей группы необязателен.
9. После сохранённого изменения инициируешь уведомление через транспорт коллеги, включая изменения от фоновой сверки времени.

### Что важно в существующем коде

- В [main.py](../../main.py) уже есть `require_admin`, `get_course_by_id`, `find_lab_config` и `find_visible_lab_config`. Повторно реализовывать разрешение ID лабы через извлечение цифр не нужно: UI может передать `short-name`, например `ЛР0.1`.
- Доступность лабораторной по правилам `join` и доступность очереди по расписанию — разные ограничения; новая очередь не должна раскрывать скрытые лабораторные.
- Студенческая `join_session` сейчас выдаётся для командной лабы, ограничена курсом/лабой и имеет cookie path `/join`. Для новых `/courses/.../queue` она автоматически не подходит. Отдельно реализуй или согласуй с автором WebSocket подходящую серверную сессию для очереди; не меняй механически область старой cookie и не связывай вход в очередь с созданием репозитория.
- Подтверждение GitHub-личности можно строить на существующем OAuth-подходе, но его текущий callback также создаёт репозитории для индивидуальных лаб. Повторно использовать его целиком как вход в очередь нельзя без явного разделения сценариев.
- `grade_lab` — существующая автоматическая проверка с возможной записью оценки. Для допуска нужна отдельная **операция чтения** результата, без вызова `/grade` и без повторной проверки с записью в таблицу.
- В [grading/sheets_client.py](../../grading/sheets_client.py) есть поиск студента и столбца лабораторной. `can_overwrite_cell` проверяет возможность перезаписи, а не успешность: инвертировать его для допуска нельзя, иначе неизвестный текст тоже станет успешной оценкой.
- Для допуска сделай отдельный разбор поддерживаемых успешных форматов: `v`, `v-N`, `v@score`, `v@score-N` с десятичной точкой/запятой. `x`, `?`, пустая ячейка и непонятный текст отклоняются. Правило чтения таблицы — твоя ответственность, его тесты тоже.
- API-вызовы фронтенда сейчас используют разные подходы: модуль `src/api/index.js` с `VITE_API_BASE_URL` и прямые `/api/v1/...` в админке. Для новой очереди выбери один общий клиент и проверь dev/Docker URL вместе с автором WebSocket.

### Студенческий интерфейс

Размести компонент рядом с работой студента с лабораторными, например в [registration-form/index.jsx](../../frontend/courses-front/src/components/registration-form/index.jsx) или на странице списка лабораторных.

Он должен показывать: доступность и причину отказа, выбранную лабораторную, кнопку записи/выхода, своё место, факт вызова, время следующего открытия при наличии, состояние загрузки/ошибки и потери соединения. После ответа сервера обновляй состояние; не считай локальное нажатие успешной записью.

Очередь студента может относиться к другой лабораторной того же курса. Общий компонент должен показать уже активную запись и не позволять обходить ограничение сменой страницы.

### Преподавательский интерфейс

Отдельный компонент управления с переходом из админки курса:

- ожидающие: ФИО, GitHub, лабораторная, время записи, порядок;
- список всех вызванных с отдельными кнопками трёх результатов;
- вызов следующего, доступный при уже вызванных;
- ручное открытие и досрочное закрытие записи;
- итоги текущего занятия и история;
- обработка пустой очереди, конфликтов, ошибок и отсутствия расписания.

Мобильная вёрстка и переводы новых текстов на ru/en/zh входят в твою задачу. Не нужно переводить весь существующий интерфейс в рамках очереди.

## 5. Контракт между тобой и коллегой

Ниже — предлагаемый интерфейс, которого ещё нет в коде. Зафиксируйте его совместно **до** реализации. Типы и ошибки лучше хранить в отдельном файле, владельцем которого будет коллега по очереди.

```python
class QueueService:
    def get_student_view(self, course_id, student, now): ...
    def get_admin_view(self, queue_id, now): ...
    def join(self, course_id, eligible_student_lab, now): ...
    def leave(self, entry_id, actor_student, now): ...
    def call_next(self, queue_id, now): ...
    def finish(self, entry_id, outcome, now): ...
    def open_manually(self, course_id, group_ids, closes_at, now): ...
    def close_registration(self, queue_id, now): ...
    def history(self, course_id, filters, cursor, limit): ...
    def reconcile(self, now): ...
```

- `student`: подтверждённый GitHub-логин и установленная сервером группа; `eligible_student_lab` дополнительно содержит ФИО и канонический ключ успешно проверенной лабы. Передавать такой объект разрешено только доверенному слою приложения.
- Ядро повторно проверяет принадлежность записи студенту, отсутствие дубликата, допустимость перехода и окно записи. Проверка роли администратора остаётся в HTTP-слое: служебные методы ядра вызываются только доверенным кодом.
- `now` — серверное время с часовым поясом, которое можно подменить в тестах; не время из тела HTTP-запроса. Долгое чтение Sheets не должно позволить проскочить закрытие записи: время для команды берётся после него и сверяется в момент изменения состояния.
- Синхронный или асинхронный интерфейс выбираете один раз. С учётом текущих sync-обработчиков и gspread проще начать с sync-ядра. Блокирующее чтение Sheets/БД нельзя переносить прямо в асинхронный WebSocket-обработчик.
- Каждая изменяющая операция возвращает результат и список `QueueChanged(queue_id, version)`. Чтение, которое выполняет сверку времени и сохраняет изменения, тоже обязано сообщить о них. Альтернатива — единый callback после commit; выберите **один** способ доставки событий.
- `reconcile` обрабатывает время идемпотентно; повторный запуск не создаёт повторных закрытий. Периодический вызов обновляет состояние без кликов, а сверка перед командами и при запуске не позволяет устаревшему состоянию пережить пропуск таймера.

Предлагаемые предметные ошибки: `QUEUE_DISABLED`, `QUEUE_CLOSED`, `ALREADY_QUEUED`, `ENTRY_NOT_FOUND`, `INVALID_STATE`, `QUEUE_EMPTY`, `GROUP_NOT_ALLOWED`, `SCHEDULE_UNAVAILABLE`. Ты добавляешь ошибки интеграции: `SESSION_REQUIRED`, `LAB_NOT_PASSED`, `STUDENT_NOT_FOUND`, `SHEETS_UNAVAILABLE`.

HTTP-соответствие: 401 — нет сессии, 403 — нет прав/допуска, 404 — объект не найден, 409 — конфликт состояния, 422 — невалидные входные данные, 503 — недоступная зависимость. Для запроса чужой записи лучше не раскрывать её содержимое; конкретный выбор 403/404 зафиксируй в контракте.

## 6. Контракты с расписанием и WebSocket

### Расписание

Автор расписания должен передавать **нормализованные занятия и правила доступности**, а не HTML и не произвольный ответ парсера. Предлагаемый результат:

```text
lesson_id, course_id, group_ids,
starts_at, ends_at, registration_opens_at,
service_until, source, schedule_revision
```

`service_until` — конец локального дня курса; это граница обслуживания, отличная от конца регистрации. Провайдер различает: нет настроенного расписания, нет занятия сегодня, ошибка получения расписания. Ошибку источника нельзя превращать в «расписания нет, записываться можно весь день».

В зоне автора расписания: один выбранный источник на курс, ручное расписание, ГУАП, интервал до начала, часовой пояс, отмены, дополнительные занятия, несколько групп в поправке и формат YAML. При ошибках он возвращает понятный результат/ошибку и описывает политику кэша; ядро не скачивает сайт вуза под блокировкой очереди.

В зоне коллеги по очереди: создать/сопоставить очередь занятию, применить ограничения, сохранить ручное закрытие/открытие, не потерять старые записи при обновлении расписания, закрыть остаток в конце дня. Удалённое из расписания занятие не должно удалять уже существующую очередь из истории.

### WebSocket

Простой вариант интеграции: **команды по HTTP, WebSocket уведомляет об изменении, клиент перечитывает состояние через HTTP**. Это рекомендация; если у автора уже другой контракт, сначала согласуйте его, не создавая второй независимый путь изменения очереди.

Минимальное уведомление: `{"type": "queue.changed", "queue_id": "...", "version": 12}`. Полные ФИО и оценки в общей рассылке не нужны.

- Уведомление публикуется после успешного сохранения, в том числе после фонового изменения. Неудачная команда не публикует успешное изменение.
- Сбой рассылки не откатывает сохранённую запись и не превращает её в неуспешную HTTP-команду.
- После подключения/переподключения и при возврате на вкладку клиент получает актуальный снимок; подписка и начальная загрузка должны учитывать изменение между ними. Версии помогают не заменить новое состояние старым ответом.
- На границе времени UI обновляется даже без нового входящего участника: через уведомление `reconcile` либо повторную загрузку по серверному времени открытия.
- Доступ к подписке проверяется на сервере; знание `queue_id` само по себе не даёт прав. Для студента без активной записи нужен канал доступности его курса/группы либо другой способ узнать об открытии очереди.
- Автор WebSocket отвечает за транспорт, аутентификацию соединения совместно с тобой, освобождение подписок и работу через reverse proxy. Ты — за связь событий с UI и вызов публикации из согласованного места приложения.

## 8. Договорённости, которые нужно зафиксировать до старта

Можно принять следующие обратимые решения; это **допущения команды**, если в issue нет более точного ответа:

1. Одна активная запись студента **в пределах курса**, независимо от группы и лабораторной; между разными курсами ограничения независимы. Преподаватель не уточнил область уникальности, поэтому обязательно указать её в PR.
2. Отдельная очередь на занятие группы, с возможностью обслуживать её до конца дня. Следующее занятие получает другую очередь; старые ожидающие в неё не переносятся. Для курса без расписания — очередь группы на день.
3. Ручное закрытие имеет приоритет над автоматическим открытием для этой очереди до явного ручного открытия; очередное выполнение таймера не отменяет решение преподавателя.
4. Выход самостоятельно разрешён только ожидающему. Результат уже вызванного ставит преподаватель.
5. Повторное завершение и повторный выход не меняют историю второй раз; поведение повторного HTTP-запроса фиксируется в API (возврат текущего результата либо стабильный конфликт).
6. На первом этапе исключаете необязательные функции: пропуск вперёд, общую очередь групп и предложение записи после проверки. Поправки расписания планируете отдельным этапом для конкурсной части.

Также до старта согласуйте конкретное хранилище, DTO, ошибки, sync/async, формат событий, интерфейс расписания и поддерживаемое число процессов backend. Новая SQLite-БД сама по себе не делает уже существующее приложение готовым к нескольким workers: ограничения других модулей сохраняются.

## 9. Последовательность работы

1. **Общий контракт.** Вместе фиксируете модели, методы, ошибки, область уникальности, расписание и авторизацию. Коллега добавляет типы и интерфейс; ты можешь писать API и UI по этим типам.
2. **Первый рабочий проход.** Коллега: записаться → место → вызов → результат → история с реальным хранилищем. Ты: подключение API и минимальные страницы. Сначала достаточно ручного тестового расписания через тот же интерфейс провайдера.
3. **Ограничения.** Ты добавляешь реальную идентификацию и чтение допуска; коллега — гонки, несколько вызванных, ограничения переходов и перезапуск.
4. **Время.** Автор расписания подключает оба источника; коллега — жизненный цикл, ты — запуск сверки и отображение доступности. Проверяете границы пары и дня.
5. **Живые обновления.** Подключаете готовый WebSocket, переподключения, уведомления от таймера, загрузку актуального снимка.
6. **Дополнение и сдача.** Поправки расписания, ru/en/zh, мобильная проверка, оба ADR, полные тесты, описание допущений и изменений в PR.

## 10. Приёмка: кто что доказывает

| Проверка | Владелец |
| --- | --- |
| Два join одного студента одновременно → одна активная запись | Коллега |
| Два call_next одновременно → разные студенты либо QUEUE_EMPTY | Коллега |
| Несколько вызванных, независимое завершение, повторная запись в конец | Коллега |
| Закрытие регистрации не удаляет ожидающих, конец дня сохраняет историю | Коллега |
| Перезапуск сохраняет очередь/историю и обрабатывает пропущенное закрытие | Коллега |
| Ручное закрытие не отменяется автоматическим таймером | Коллега + автор расписания |
| Чужая запись, поддельная личность, админский вызов без сессии отклоняются | Ты |
| `v` и успешные варианты допускаются; `x`, `?`, пустота и мусор — нет | Ты |
| Ни одна операция очереди не пишет в ячейки оценок, включая завершение | Ты; отдельный интеграционный тест |
| Нет занятия / нет расписания / ошибка провайдера различаются | Автор расписания + ты |
| Отмена, дополнительное занятие, перенос и сохранность старых записей | Автор расписания + коллега |
| Две вкладки видят изменение; после разрыва соединения состояние восстанавливается | Ты + автор WebSocket |
| Без пользовательских запросов наступление границы времени меняет состояние | Коллега + ты + автор WebSocket |
| Удобство на телефоне, переводы, сборка frontend | Ты |

Общая демонстрация: два разных студента с успешно проверенными лабораторными записываются; видят места; преподаватель вызывает обоих до завершения первого; независимо завершает с разными исходами; один записывается повторно в конец; после закрытия пары новая запись отклоняется, ожидающих ещё можно принять; после перезапуска история остаётся. Повторить ключевую часть на телефоне и при переподключении WebSocket.

Каждый запускает тесты своего слоя. Перед сдачей команда запускает существующий backend-набор, frontend-тесты и production build по инструкциям проекта; новые сбои исправляет владелец слоя. Проверьте сценарий через реальный frontend/proxy, а не только отдельные функции.
