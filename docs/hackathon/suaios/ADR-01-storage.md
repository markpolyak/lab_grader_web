# ADR: хранение очередей и истории в SQLite

- **Команда:** suaios
- **Статус:** принято командой.
- **Дата:** 2026-11-07.

## Контекст

Студент подтверждает посещение, преподаватель вызывает ожидающих и отмечает результат каждой защиты. Преподаватель может принимать нескольких студентов одновременно. Требуется сохранить допуск, посещение, состав занятия, попытки и историю после перезапуска. Несколько групп и пересекающиеся пары должны иметь раздельные списки.

Backend уже работает на FastAPI; маршруты находятся в [main.py](../../../main.py). [QueueStore](../../../grading/defense_queue/storage.py) обслуживает короткие транзакции без сетевых запросов внутри. Фоновый [worker](../../../grading/defense_queue/worker.py) сверяет данные Google Sheets через десять минут после окончания занятия и повторно в местную полночь; срок, попытки и ошибки сверки тоже нужно сохранять. Один пользователь может иметь одну активную попытку по предмету, но несколько разных студентов могут защищаться параллельно.

[Задание #62](https://github.com/markpolyak/lab_grader_web/issues/62) требует историю и запрещает отдельно разворачиваемые сервисы. В ответе преподаватель разрешил SQLite при обосновании в ADR. Очередь не записывает результаты защиты в ячейки оценок: их ведёт преподаватель. Команда сохраняет собственную политику −1 и фиксацию состава в начале занятия; эти отличия от задания требуют отдельного указания при сдаче.

Данные хранятся в `QUEUE_DB_PATH` (по умолчанию `data/queue.sqlite3`). Автоматического удаления истории в первой версии нет; владелец сервиса определяет срок хранения и резервного копирования. Персональные данные нельзя добавлять в Git.

## Рассмотренные варианты

### Вариант 1: память процесса

Backend хранит словари участников, занятия и события в RAM.

- **Плюсы:** нет файлов, миграций и внешних зависимостей.
- **Минусы:** после перезапуска пропадут посещение, порядок, результаты и задания сверки. Несколько процессов получат разные очереди.
- **Что потребует от проекта:** блокировки внутри процесса; для долговечности всё равно потребуется отдельное хранилище.

### Вариант 2: JSON-файлы

Backend сохраняет снимок очереди и журнал событий на диске.

- **Плюсы:** формат читается обычным редактором; не нужен сервер БД.
- **Минусы:** придётся реализовать атомарную замену, межпроцессные блокировки, восстановление после сбоя между записью попытки и события. Проверка одной активной записи становится прикладной логикой.
- **Что потребует от проекта:** свой протокол записи и миграций; синхронизация снимка и журнала; тесты повреждённых и частично записанных файлов.

### Вариант 3: SQLite

Backend выполняет связанные изменения в одной транзакции. Уникальные ограничения защищают от дублирования активных попыток, внешние ключи связывают занятия, студентов и историю.

- **Плюсы:** транзакции, ограничения, индексы и Backup API доступны через стандартный `sqlite3`; отдельный сервис не нужен. После перезапуска остаются очередь, события и незавершённые задания сверки.
- **Минусы:** одновременно пишет один writer; нужны короткие транзакции и корректная резервная копия. WAL рассчитан на общий локальный диск, а не несколько хостов.
- **Что потребует от проекта:** каталог данных с правом записи, `QUEUE_DB_PATH`, миграции и резервное копирование. В Docker используется постоянный том. Для запуска без Docker достаточно локального файла с нужными правами.

## Решение

Команда выбрала SQLite. Ограничения БД и транзакции закрывают требования долговечности и конкурентных действий без нового сервиса. Память не сохраняет историю при перезапуске; JSON потребовал бы собственного механизма транзакций.

[Миграции](../../../grading/defense_queue/migrations) создают:

| Сущность | Назначение |
|---|---|
| `courses`, `study_groups` | предмет, группа и часовой пояс |
| `students`, `course_students` | студент и его связь с предметом/группой |
| `queue_candidates` | первая обязательная работа, допущенная к защите |
| `sessions` | логическое занятие со стабильным ID и изменяемым временем |
| `session_participation` | ответ о посещении и момент фиксации |
| `queue_entries` | отдельная попытка защиты и её результат |
| `queue_events` | неизменяемая история действий и снимков |
| `queue_reconciliations`, `queue_sync_state` | долговечная сверка и последний результат чтения |
| `queue_settings` | ручные настройки курса |
| `queue_commands` | идентификаторы команд вызова для безопасного повтора HTTP-запроса |

Состояния попытки: `waiting`, `called`, `defended`, `failed`, `no_show`, `withdrawn`, `expired`. Результат относится к конкретной попытке. После неудачи повторная попытка попадает в конец. Индекс допускает одну активную попытку студента на предмет; ограничения «один вызванный на преподавателя» больше нет. Миграция 005 снимает его и сохраняет существующие данные.

`BEGIN IMMEDIATE` сериализует изменения. Обновление попытки и событие попадают в одну транзакцию. Backend читает Google Sheets и расписание за пределами этой транзакции; квота сети не удерживает блокировку записи.

## Последствия

### Что становится проще

После перезапуска преподаватель продолжает работу с сохранёнными попытками. Повтор команды с тем же `request_id` возвращает прежний вызов. Новый `request_id` вызывает следующего, даже если предыдущая защита продолжается. Копирование через SQLite Backup API захватывает данные активного WAL.

### Что становится сложнее или невозможным

Владелец сервиса отвечает за права каталога, резервные копии и восстановление. Обычное копирование только основного файла во время записи ненадёжно. Несколько хостов не могут использовать этот файл как распределённую БД.

### Известные ограничения и риски

- **Перезапуск:** зафиксированные изменения сохраняются, незавершённая транзакция откатывается. Фоновая сверка подхватывает сохранённые задания. Ранняя сверка сохраняет `checked_at` и назначает ночное чтение; `done_at` заполняется после финального чтения.
- **Несколько процессов:** SQLite обеспечивает ограничения и сериализацию, сверка использует lease. Однако текущая конфигурация приложения рассчитана на один backend worker: соседние модули сервиса сохраняют задания в памяти. Полное масштабирование всего приложения этим ADR не подтверждается.
- **Одновременные запросы:** уникальный индекс и транзакция запрещают две активные попытки одного студента; несколько разных студентов могут находиться в `called`. Долгие транзакции способны вызвать `SQLITE_BUSY`; сеть вынесена за их пределы.
- **Сбой Sheets/GitHub или квота:** очередь показывает сохранённый состав; новые допуски требуют свежих данных. Сверка сохраняет ошибку и повторяет попытку. Модуль очереди не исправляет оценки.
- **Идентификация:** существующая форма ФИО/GitHub не подтверждает владельца аккаунта. Команда приняла этот риск; SQLite его не устраняет.

### Как проверить

[HTTP-сценарии](../../../tests/test_queue_journey.py): повтор посещения, защита, повторная попытка, сверка, backup/restore, конкурентный повтор одной команды. [Хранилище](../../../tests/test_defense_queue_storage.py): ограничения и перезапуск. [Регрессии](../../../tests/test_defense_queue_audit.py): атомарность и восстановление.

## Что пришлось бы изменить, если...

- **Несколько аудиторий:** назначить разные `teacher_key`/занятия, если это разные преподаватели; для одного преподавателя несколько вызванных уже разрешены. Если потребуется отдельная роль ассистента, добавить права и связь с занятиями.
- **Несколько процессов:** проверить блокировки остальных модулей, дубли фоновых задач и работу одного локального файла. Для нескольких хостов выбрать серверную СУБД и изменить слой хранения.
- **Ограниченный срок хранения:** добавить политику архивации и удаления связанных событий с проверкой требований к персональным данным.
