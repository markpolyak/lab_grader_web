# ADR: Хранение очереди на защиту и её истории в Google Sheets

- **Команда:** toyota-skyline: Антонушкина Ева, Бандуков Михаил, Юрченко Артём
- **Статус:** принято
- **Дата:** 2026-11-08

## Контекст

Лабораторные работы сдаются на занятии: студент записывается в очередь,
преподаватель вызывает по списку и отмечает результат (сдал / не сдал /
не явился). Очередь живёт один учебный день, после чего результат
защиты переносится в архив.

Проект `lab_grader_web` уже использует Google Sheets как хранилище
оценок: в таблице курса есть листы-группы (`4431`, `4432`), где
в колонках стоят оценки по лабораторным. Добавлять отдельное хранилище
данных для очереди означало бы расширить технологический стек и
поддерживать два источника правды.

- **Что хранить:** дневная очередь (позиция, группа, ФИО, ЛР, № пары,
  статус) и архив (то же + дата). Очередь живёт до конца дня, архив —
  навсегда.
- **Кто читает:** студенты — свой статус и позицию (часто, при каждом
  обновлении страницы); преподаватель — весь список очереди (постоянно
  во время занятия).
- **Кто пишет:** студенты — записываются, выходят, сдвигаются
  (несколько раз за занятие); преподаватель — отмечает результат защиты
  (для каждого студента один раз в конце).
- **Ограничения:** backend запущен в одном процессе (один gunicorn
  worker, см. `docker-compose.yml`); внешние API — GitHub и Google
  Sheets, у последнего квота ~60 запросов/мин на проект; хранилище
  данных не развёрнуто (нет PostgreSQL/SQLite volume); курс
  конфигурируется YAML-файлами в `courses/`.

## Рассмотренные варианты

### Вариант 1: SQLite (отдельная база данных)

База данных SQLite в volume Docker, таблицы `queue_entries` и
`queue_history`, ORM (SQLAlchemy или raw SQL).

- **Плюсы:**
    - Структурированные данные, транзакционность, индексы.
    - Не зависит от квот Google Sheets API.
    - SQL-запросы для аналитики (сколько сдало за семестр).
- **Минусы:**
    - Новый источник правды: оценки в Google Sheets, очередь в SQLite —
      два места, которые надо синхронизировать.
    - Volume в Docker, миграции схемы, backup.
    - Преподаватель не может посмотреть очередь прямо в таблице —
      нужен веб-интерфейс.
    - Усложнение развёртывания и проекта для хакатона.
- **Что потребует от проекта:** зависимость `sqlalchemy`, файл
  `queue.db` в volume (`docker-compose.yml`), миграции, отдельная
  логика резервного копирования.

### Вариант 2: In-memory кеш (RAM)

Очередь хранится в словаре Python в памяти процесса, периодически
сбрасывается в Google Sheets как backup.

- **Плюсы:**
    - Максимально быстро, нет обращений к API при чтении.
    - Нет новых зависимостей.
- **Минусы:**
    - При перезапуске backend очередь теряется — неподъёмно во время
      занятия: 20 студентов записались, процесс упал, все данные пропали.
    - Кеш (`grading/queue/cache.py`) уже есть, но он — read-through
      поверх Sheets, а не первоисточник.
    - Если процесс один (как сейчас) — нет отказоустойчивости; если
      несколько — нет общего состояния без внешнего хранилища.
- **Что потребует от проекта:** логику периодического сброса в Sheets,
  обработку рассинхронизации между кешем и таблицей после перезапуска.

### Вариант 3: Google Sheets (выбран)

Ежедневный лист `Очередь-YYYY-MM-DD` в таблице курса. Лист
`История_очереди` — append-only архив. Backend читает и пишет через
gspread, кеширует чтение в памяти с TTL 30 секунд
(`grading/queue/cache.py`). Мьютекс `sheet_lock(spreadsheet_id)`
(`grading/queue/locks.py`) сериализует мутации.

- **Плюсы:**
    - Один источник правды: оценки и очередь в одной таблице.
    - Преподаватель видит очередь прямо в Google Sheets — без
      веб-интерфейса, с filter views по статусам и парам.
    - Архив — append-only лист в той же таблице, виден преподавателю.
    - Нет новых зависимостей: gspread уже используется.
    - Конфликт-листы и schema-mismatch проверяются при открытии
      (`grading/queue/store.py:158-181`).
- **Минусы:**
    - Квота Google Sheets API (~60 запросов/мин) — кеш сглаживает,
      но при пиковой нагрузке (вся группа одновременно) возможны
      задержки.
    - Нет транзакций: `batch_update` атомарен, но последовательность
      «прочитать → изменить → записать» — нет. Мьютекс решает только
      в рамках одного процесса.
    - Лист создаётся при первом обращении в день — если два запроса
      придут одновременно, Google Sheets может создать conflict-лист
      с суффиксом `_conflict{timestamp}`.
- **Что потребует от проекта:** ничего нового — gspread, itsdangerous
  и slowapi уже в зависимостях.

## Решение

Выбран **вариант 3 (Google Sheets)**.

Главная причина: проект уже хранит оценки в Google Sheets, и очередь
на защиту — часть того же учебного процесса. Добавление SQLite или
другого хранилища создавало бы второй источник правды, требовало
синхронизации и усложняло развёртывание. Преподаватель работает с
таблицей напрямую — filter views, dropdown для статусов, ручное
редактирование — и не должен учить отдельный интерфейс.

Кеш (`grading/queue/cache.py`) с TTL 30 секунд снижает количество
обращений к API. Мьютекс (`grading/queue/locks.py`) гарантирует, что
мутации внутри одного процесса сериализованы.

## Последствия

### Что становится проще

- Преподаватель видит очередь в знакомом интерфейсе Google Sheets.
- Архив — простой append-only лист, не нужна отдельная БД для истории.
- Filter views по статусам («Все ждёт», «Сдано», «Не сдал») и парам
  («Пара 1»–«Пара 6») — создаются автоматически при открытии листа.
- Data validation (dropdown) на колонке «Статус» — преподаватель
  выбирает из списка, опечатки исключены.
- Apps Script (`apps-script/Code.gs`) автоматизирует закрытие дня и
  очистку conflict-листов — не требует backend.

### Что становится сложнее или невозможным

- Масштабирование на несколько процессов backend — мьютекс
  `threading.RLock` работает только внутри одного процесса. Нужен
  внешний lock (Redis SETNX) или single-worker ограничение.
- Аналитика по архиву — нет SQL-запросов, только ручной просмотр
  листа `История_очереди` или экспорт.
- Одновременная запись — если два запроса меняют позицию в очереди,
  мьютекс сериализует их, но это создаёт задержку при пиковой нагрузке.

### Известные ограничения и риски

- **Backend перезапустился во время занятия:** кеш теряется, но данные
  в Google Sheets сохраняются. При первом обращении после рестарта кеш
  перестраивается. Студенты не теряют записи в очереди.
- **Запущено больше одного процесса backend:** мьютекс не работает
  между процессами — две мутации могут одновременно записать в один
  лист и перетереть данные. Решение: `--workers 1` в gunicorn (уже
  зафиксировано в `docker-compose.yml`). Для масштабирования — внешний
  lock.
- **Два запроса одновременно меняют одну очередь:** мьютекс
  `sheet_lock(spreadsheet_id)` сериализует. Запросы ставятся в очередь
  и выполняются последовательно. Задержка — миллисекунды.
- **Google Sheets недоступен:** endpoint возвращает 503
  (`main.py:_open_spreadsheet`). Кеш продолжает отдавать последние
  данные до истечения TTL. После восстановления — перестраивается.
- **Conflict-лист:** если Google Sheets создал лист с суффиксом
  `_conflict`, Apps Script очищает их (`cleanupConflictSheets`), а
  `_ensure_sheet` в `store.py` удаляет conflict-листы перед созданием.
- **Квота Google Sheets API превышена:** запросы замедляются. Кеш с TTL
  30 секунд снижает количество обращений: типичная нагрузка — 10–20
  студентов, 5–10 обращений в минуту, укладывается в квоту.

### Как проверить

- `tests/test_queue_store_advanced.py` — тесты `register`, `withdraw`,
  `shift_down`, `set_status` с FakeSpreadsheet.
- `tests/test_queue_endpoints.py` — endpoint-тесты: статус, регистрация,
  отказ, сдвиг, список, admin set-status, snapshot.
- `tests/test_queue_store_advanced.py::test_snapshot_writes_history_and_deletes_daily_tab_atomically`
  — snapshot переносит записи в историю и удаляет лист.

## Что пришлось бы изменить, если...

- ...очередь нужно вести одновременно в нескольких аудиториях:
  добавить колонку «Аудитория» в `QUEUE_HEADERS`, filter view по
  аудитории. Лист остаётся один на день.
- ...backend нужно масштабировать на несколько процессов: заменить
  `threading.RLock` на Redis `SETNX` с TTL. Кеш — на Redis или общий
  in-memory store. Логика store.py не меняется, только слой блокировки.
- ...нужна аналитика по архиву (сколько сдало за семестр): добавить
  endpoint, который читает `История_очереди` через gspread и агрегирует
  в Python. Или экспортировать в CSV и обрабатывать внешним
  инструментом.
