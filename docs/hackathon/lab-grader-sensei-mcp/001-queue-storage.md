# ADR: хранение очередей и истории

- **Команда:** lab-grader-sensei-mcp
- **Участники:** указать состав команды перед сдачей
- **Статус:** принято
- **Дата:** 2026-11-08

## Контекст

Очередь на защиту лабораторных должна переживать перезапуск backend и
сохранять историю защит. При этом проект по требованиям хакатона нельзя
существенно усложнять и нельзя добавлять внешние сервисы, которые нужно
отдельно разворачивать и сопровождать.

Что требуется хранить:

- очередь занятия: курс, группы, привязку к занятию и его времени, окно
  записи, ручной режим, версию состояния;
- записи студентов: подтверждённый GitHub-логин, ФИО, группу, лабораторную,
  время записи, порядковый номер, статус, время вызова и завершения,
  результат защиты;
- историю: завершённые, отменённые и истёкшие записи должны оставаться
  доступными преподавателю после закрытия занятия и после перезапуска.

Ограничения проекта:

- backend работает в одном процессе; несколько workers не поддерживаются
  (это уже ограничение `grading/propagate.py`, `grading/bulk.py` и
  `QueueService`);
- в проекте нет БД; внешние сервисы разворачивать нельзя;
- расписание уже хранится в YAML-файлах и обновляется фоновым парсером;
- SQLite формально допустим по ответу преподавателя, но требует отдельного
  обоснования и усложняет развёртывание;
- очередь не должна писать в Google Sheets: оценки выставляет преподаватель.

Дополнительно: после защиты или выхода студент должен иметь возможность
записаться снова. Поэтому завершённые записи нельзя удалять — они нужны и
для истории, и для правила «одна активная запись».

## Рассмотренные варианты

### Вариант 1: только память процесса

`Lesson.queue` и `QueueRecord` живут только в памяти, как это было в
начальном каркасе.

- **Плюсы:** ничего не нужно настраивать; минимальная задержка; нет файловых
  операций.
- **Минусы:** перезапуск backend полностью теряет очередь и историю;
  требование «записи сохраняются» не выполняется; при сбое процесса студенты
  теряют места.
- **Что потребует от проекта:** ничего, но и требуемого поведения не даёт.

Отклонён: противоречит обязательному требованию сохранности.

### Вариант 2: один общий YAML/JSON-файл на все очереди

Все `QueueRecord` лежат в одном файле, при каждом изменении файл
перезаписывается целиком.

- **Плюсы:** просто читать и инспектировать; один файл легко скопировать.
- **Минусы:** любое изменение переписывает все очереди; повреждение одного
  файла теряет всё; при росте истории файл быстро становится большим;
  параллельные записи сериализуются на одном файле; хуже ложится на будущую
  замену БД.
- **Что потребует от проекта:** отдельный формат, блокировку и резервное
  копирование всего файла.

Отклонён: слишком большая зона поражения при сбое и лишняя перезапись.

### Вариант 3: файл на очередь + порт репозитория (выбран)

Один YAML-файл на очередь в каталоге `QUEUE_STATE_DIR` (по умолчанию
`queue_state`), доступ через `QueueRepository`. Файл создаётся лениво, при
первом изменении очереди. Запись атомарная, версия проверяется через
`expected_version`.

- **Плюсы:** перезапуск backend не теряет состояние; повреждение одного
  файла не затрагивает остальные; нет новых зависимостей и сервисов;
  человекочитаемый формат; интерфейс репозитория позволяет позже заменить
  файлы на SQLite/Postgres без изменения `QueueService` и HTTP-слоя.
- **Минусы:** нет транзакций между очередями; несколько процессов не
  поддерживаются; файл истории растёт вместе с очередью; нужна аккуратная
  атомарная запись.
- **Что потребует от проекта:** `QUEUE_STATE_DIR`, постоянный volume в
  production, сериализация `QueueRecord`, тесты на атомарность и версии.

Выбран.

### Вариант 4: SQLite

Встроенная БД в файле, SQL-транзакции, отдельный адаптер за тем же портом.

- **Плюсы:** настоящие транзакции, удобные выборки истории, лучше подходит
  для нескольких процессов, чем файлы.
- **Минусы:** новая зависимость/драйвер, миграции, отдельный файл БД и volume,
  больше кода и документации; для одного процесса и текущего объёма данных
  выигрыш не оправдывает усложнения.
- **Что потребует от проекта:** схема, миграции, настройка хранения,
  резервное копирование.

Отложен, не отклонён: интерфейс `QueueRepository` уже позволяет добавить
SQL-адаптер позже.

## Решение

Выбран **вариант 3**: файл на очередь + синхронный порт `QueueRepository`.

### Интерфейс

`queues/usecase/port/queue_repositories.py`:

```python
class QueueRepository(Protocol):
    def create(self, queue: QueueRecord) -> QueueRecord: ...
    def get(self, queue_id: UUID) -> QueueRecord | None: ...
    def save(self, queue: QueueRecord, *, expected_version: int) -> QueueRecord: ...
    def list_by_course(self, course_id: str, *, group_id: str | None = None) -> list[QueueRecord]: ...
```

Реализации:

- `queues/repositories/storage/file/FileQueueRepository` — рабочее хранилище;
- `queues/repositories/storage/inmemory/InMemoryQueueRepository` — тестовый
  адаптер и значение по умолчанию для `QueueService()` в unit-тестах;
- SQL-адаптер — возможное будущее расширение, интерфейс уже готов.

### Формат и расположение

```text
QUEUE_STATE_DIR/
  <queue_id>.yaml
```

`queue_id` сейчас совпадает с `lesson.id`. Один файл на очередь, а не на
курс: `get(queue_id)` не должен знать курс, а `list_by_course` обходит
каталог и фильтрует по `course_id` внутри файла. Для текущего количества
очередей (единицы занятий на неделю) это дешевле и безопаснее, чем один
общий файл.

Сериализация явная (`queues/repositories/storage/file/serialization.py`):

- `UUID` → строка, `datetime` → ISO-строка;
- `EntryStatus`, `DefenseResult`, `RegistrationMode` → их строковые значения;
- `entry_metadata` с UUID-ключами сохраняется и восстанавливается;
- отсутствующие необязательные поля читаются как `None`.

### Гарантии записи

- временный файл создаётся в том же каталоге, что и целевой;
- `flush()` + `os.fsync()` перед `os.replace()`; замена атомарна в пределах
  одной ФС;
- `RLock` в адаптере сериализует `create/get/save/list_by_course`;
- `save` проверяет `version` текущего файла и `expected_version`, при
  расхождении поднимает `QueueVersionConflictError`;
- `create` не перезаписывает существующий файл;
- повреждённый YAML не перезаписывается молча: файл переименовывается в
  `*.corrupt-<timestamp>`, поднимается `QueueStorageCorruptedError`;
  `list_by_course` пропускает повреждённый файл, чтобы не скрывать остальные.

### Связь с `QueueService`

- при загрузке недели `QueueService` строит `Lesson` из YAML расписания и
  поднимает сохранённый `QueueRecord` по `lesson.id`;
- `_records` — рабочая копия в памяти; файл — источник истины между
  перезапусками;
- любая мутация (`join`, `leave`, `call_next`, `finish`,
  `set_registration`) завершается `save_lesson`, то есть write-through:
  HTTP-ответ отправляется только после записи файла;
- завершённые и отменённые записи остаются в `QueueRecord.queue.entries` со
  статусами в `entry_metadata`; поэтому история доступна, а повторная запись
  разрешена (проверка дубликата смотрит только `waiting`/`called`);
- `QueueService._lock` защищает публикацию расписания и мутации в одном
  процессе; сетевые вызовы (Sheets, GitHub) под этим lock не выполняются.

## Последствия

### Что становится проще

- Очередь и история переживают перезапуск backend.
- Нет новых сервисов и зависимостей: PyYAML уже используется расписанием.
- Файл можно открыть и посмотреть глазами; отдельная очередь чинится или
  удаляется независимо от остальных.
- Замена на SQLite/Postgres — новый класс за `QueueRepository`, без
  изменений HTTP-ручек и домена.

### Что становится сложнее или невозможным

- Несколько процессов backend не поддерживаются: `RLock` и версия работают
  только внутри одного процесса. Это осознанное ограничение, как и у
  остальных модулей проекта.
- Нет транзакций между очередями: инвариант «одна активная запись на курс»
  проверяется в `QueueService` под его lock; при переходе на БД его нужно
  будет проверять запросом/транзакцией.
- История хранится в том же файле, что и очередь; со временем файл растёт.
- В запросе регистрации версия пока не передаётся: в одном процессе запись
  сериализуется lock'ом; для нескольких процессов понадобится `If-Match`/
  `version` и ответ `409 VERSION_CONFLICT`.

### Известные ограничения и риски

- **backend перезапустился во время занятия.** Очередь и история
  восстанавливаются из файлов; `Lesson` пересоздаются из YAML расписания,
  очередь привязывается по `lesson.id`. Записи, не успевшие сохраниться до
  падения, теряются — окно ограничено временем между мутацией и ответом.
- **запущено больше одного процесса backend.** Каждый процесс читает и
  пишет файлы независимо; корректной синхронизации нет. Требуется один
  worker либо замена адаптера на БД.
- **два запроса одновременно меняют одну очередь.** В одном процессе
  `QueueService._lock` сериализует операции; `save(expected_version)`
  дополнительно не даёт затереть чужое изменение. В нескольких процессах
  возможен `QueueVersionConflictError`, который нужно обработать на клиенте.
- **Google Sheets или GitHub недоступны.** Хранилище очереди от них не
  зависит; операции очереди продолжают работать. Допуск студента к записи
  (чтение Sheets) в это время вернёт `503 SHEETS_UNAVAILABLE`.
- **файл повреждён.** Он откладывается в `*.corrupt-*`, ошибка пишется в лог;
  остальные очереди продолжают читаться. Восстановление повреждённого файла
  вручную — ответственность администратора.
- **питание пропало во время записи.** `os.replace` не оставляет
  полузаписанный целевой файл; `fsync` файла снижает риск, но каталог
  отдельно не синхронизируется. Для хакатонного решения это принято как
  допустимое.

### Как проверить

- `queues/tests/test_file_queue_repository.py` — round-trip всех полей,
  восстановление новым экземпляром репозитория, версии, конкурентные
  `save`, повреждённый файл, отсутствие временных файлов,
  `QUEUE_STATE_DIR`;
- `queues/tests/test_queue_service_storage.py` — ленивое создание файла,
  восстановление после «рестарта», инкремент версии, сохранение ручного
  режима, повторная запись;
- `queues/tests/test_queue_repository.py` — общий контракт репозитория;
- `queues/tests/test_queue_operations.py` — статусы, повторная запись,
  история;
- `tests/test_queue_admin_endpoints.py`,
  `tests/test_queue_student_endpoints.py` — HTTP-сценарии.

## Что пришлось бы изменить, если...

- **...очередь нужно вести одновременно в нескольких аудиториях.** Сейчас
  очередь одна на занятие (`lesson.id`). Понадобится ключ «занятие +
  аудитория» в `Lesson`/`QueueRecord` и отдельный файл на такую очередь;
  интерфейс репозитория менять не нужно.
- **...backend нужно масштабировать на несколько процессов.** Заменить
  `FileQueueRepository` на SQL-адаптер с транзакциями и блокировками;
  добавить `version`/`If-Match` в изменяющие HTTP-запросы; перенести
  периодическую сверку времени в один выделенный процесс.
- **...историю нужно редактировать или удалять.** Файлы — не append-only
  журнал; понадобится отдельный журнал аудита или БД с ограничениями
  доступа.
- **...появится требование хранить очередь в БД по инфраструктурным
  причинам.** Реализовать `SqlQueueRepository` за тем же портом; сериализация
  в YAML останется только у файлового адаптера.
- **...понадобится резервное копирование.** Достаточно копировать каталог
  `QUEUE_STATE_DIR`; для production его нужно вынести на постоянный volume.
