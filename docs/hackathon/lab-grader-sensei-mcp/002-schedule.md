# ADR: расписание и подключение источников

- **Команда:** lab-grader-sensei-mcp
- **Участники:** указать состав команды перед сдачей
- **Статус:** принято
- **Дата:** 2026-11-08

## Контекст

Очередь должна открываться и закрываться по расписанию занятий, а занятия
должны быть доступны без похода на сайт вуза в момент запроса студента.
По требованиям:

- для курса выбирается один источник расписания: модуль вуза либо ручное
  расписание в конфигурации курса;
- у сайта ГУАП нет JSON API; разрешён открытый парсер, в том числе как
  справочник по устройству сайта;
- получение расписания должно быть модульным: для другого вуза достаточно
  добавить модуль источника и указать его в конфигурации курса;
- расписание должно переживать недоступность сайта вуза;
- интервал открытия записи до начала пары настраивается; преподаватель
  назвал 15 минут разумным значением, но не жёсткой константой;
- дополнение от 06.11.2026 требует заранее задаваемых поправок: отменённых
  и дополнительных занятий для указанных групп.

Текущее состояние проекта:

- `queues/parser/parser.py` содержит `ScheduleParser` и провайдер `suai`,
  который использует заимствованный парсер сайта ГУАП;
- парсер сохраняет нормализованное расписание в
  `schedule/<university>/<semester>/<teacher>.yaml`;
- `QueueService` читает эти YAML, сопоставляет занятия с курсами и строит
  `Lesson` с очередями;
- `GET /courses/{course_id}/lessons` отдаёт занятия текущей недели без
  обращений к сети;
- автоматическое открытие/закрытие записи по времени и поправки расписания
  пока **не реализованы**; есть только ручное открытие/закрытие очереди
  через админский API.

## Рассмотренные варианты

### Вариант 1: парсить сайт вуза на каждый запрос

`GET /lessons` и операции очереди каждый раз скачивают и разбирают страницы
ГУАП.

- **Плюсы:** всегда самые свежие данные; не нужно хранить выгрузку.
- **Минусы:** сетевой вызов в пользовательском запросе; сайт может быть
  недоступен; нет офлайн-режима; очередь зависит от чужого HTML; высокая
  задержка и риск блокировки при массовых запросах.
- **Что потребует от проекта:** кэш, таймауты, повторные попытки, защиту от
  одновременных загрузок.

Отклонён: ставит доступность очереди в зависимость от внешнего сайта.

### Вариант 2: только ручное расписание в конфигурации курса

Преподаватель или администратор вручную ведёт YAML с занятиями.

- **Плюсы:** полностью контролируемо; нет парсера и сети; удобно для
  нештатных занятий и небольших курсов.
- **Минусы:** для ГУАП это ручной труд каждую неделю; ошибки ввода;
  требования прямо просят автоматическое получение расписания вуза.
- **Что потребует от проекта:** формат YAML и редактирование конфигурации,
  но не решает основную задачу.

Отклонён как единственный источник: не масштабируется на реальное
расписание ГУАП.

### Вариант 3: фоновый парсер + нормализованный YAML-снимок (выбран)

`ScheduleParser` периодически обновляет YAML-выгрузку, `QueueService`
читает только локальный снимок. Ручное/офлайн-расписание — тот же формат
YAML, но без сетевого парсера.

- **Плюсы:** пользовательские запросы не ходят в сеть; сайт вуза может быть
  недоступен, очередь продолжает работать на последней выгрузке; формат
  можно читать глазами и версионировать; новый вуз — новый провайдер, а не
  изменения в очереди.
- **Минусы:** данные могут отставать на интервал обновления; нужен
  планировщик и постоянный каталог; при нескольких процессах каждый
  запустит свой планировщик; нет поправок расписания «из коробки».
- **Что потребует от проекта:** каталог `schedule/`, настройки в
  `schedule/index.yaml`, volume в production, аккуратная атомарная запись.

Выбран.

## Решение

Выбран **вариант 3**: фоновый парсер пишет нормализованный YAML, очередь
читает локальный снимок.

### Источники и конфигурация

- `schedule/index.yaml` задаёт источники: вуз, преподавателя, семестр
  (вручную или `auto`), часовой пояс, интервал обновления;
- сейчас поддерживается `university: suai`; провайдеры подключаются в
  `ScheduleParser.providers`;
- для ручного/офлайн-режима используется тот же формат YAML и
  `SCHEDULE_CONFIG=schedule/offline.yaml`; сетевой парсер при этом не
  запускается;
- `SCHEDULE_DIR` задаёт каталог выгрузок.

### Обновление

- `ScheduleParser` пишет файл атомарно: временный файл в том же каталоге +
  `os.replace`; при ошибке сети/парсинга старый YAML сохраняется;
- APScheduler запускает проверку срока обновления (по умолчанию раз в час);
- независимая задача `queue-schedule-sync` раз в минуту перечитывает
  локальные YAML, подхватывает ручные правки и переключает неделю в
  понедельник 00:00 по Москве;
- при ошибке YAML прежнее состояние остаётся в памяти, попытка повторяется
  на следующем запуске.

### Построение занятий и очередей

`QueueService.generate_week`:

- берёт только активные курсы ГУАП/СУАИ;
- сопоставляет `subject` из YAML с `name` курса;
- для занятия считает стабильный `lesson_id` из
  `(course_id, starts_at, ends_at, groups, kind)`; смена аудитории не
  создаёт новую очередь;
- создаёт `Lesson` с одной `Queue` на занятие; для занятия нескольких групп
  очередь общая;
- сохраняет объекты прошлых недель и убранные занятия в `_lessons`, чтобы
  при повторном появлении использовать прежнюю очередь;
- публикует только текущую неделю в `Schedule.lessons`.

`GET /courses/{course_id}/lessons` и админские ручки читают этот снимок;
они не обращаются к сайту вуза и Google Sheets.

### Граница с очередью

Фактическая граница сейчас — `ScheduleParser` (запись YAML) и
`QueueService` (чтение и построение `Lesson`). Отдельный
`ScheduleProvider`/`SchedulePolicy` как формальный `Protocol` пока не
выделен. Предлагаемая будущая граница:

```python
lessons_for_week(course_id) -> list[Lesson]
get_lesson(queue_id) -> Lesson | None
availability(lesson, now) -> RegistrationState
service_until(lesson, now) -> datetime
```

Это позволит автору расписания менять источники и окна, не затрагивая
операции очереди.

## Последствия

### Что становится проще

- Пользовательские запросы не зависят от доступности сайта вуза.
- Ошибка парсера не ломает очередь: используется последняя успешная выгрузка.
- Новый вуз добавляется провайдером и конфигурацией, без изменений в
  `QueueService`.
- Формат YAML можно инспектировать и править вручную.

### Что становится сложнее или невозможным

- Расписание может отставать на интервал обновления; для ГУАП это
  компромисс между свежестью и нагрузкой на сайт.
- Поправки (отмены и дополнительные занятия) пока не реализованы; формат
  поправок нужно описать в `docs/COURSE_CONFIG.md`.
- Автоматическое открытие записи за 15 минут и закрытие по концу пары пока
  не реализовано: есть только ручной режим `Queue.closed` через админский
  API. Окна записи должны появиться в `ScheduleProvider`/`SchedulePolicy`.
- Несколько процессов backend запустят несколько планировщиков; проект уже
  требует один worker.
- После перезапуска восстанавливаются только занятия текущей недели;
  прошлые занятия и их очереди остаются в файлах очередей, но не в
  `service.schedules`.

### Известные ограничения и риски

- **сайт вуза недоступен.** Старый YAML сохраняется, очередь работает;
  обновление повторится на следующей проверке.
- **YAML повреждён или правится вручную.** Локальная синхронизация
  пропускает обновление, прежнее состояние сохраняется; ошибка попадает в
  лог.
- **backend перезапустился.** Занятия пересоздаются из YAML, очереди
  поднимаются из `QUEUE_STATE_DIR` по `lesson_id`; записи, не попадавшие в
  файл, теряются.
- **запущено больше одного процесса backend.** Каждый процесс запускает свой
  планировщик и перечитывает YAML независимо; это может приводить к лишним
  запросам к сайту вуза. Ограничение одно процесса.
- **занятие перенесли или отменили.** Без поправок расписание вуза может
  содержать устаревшее занятие; уже записавшиеся не удаляются, но новая
  запись идёт по текущей выгрузке.
- **часовой пояс.** Время занятия хранится с часовым поясом из YAML
  (`Europe/Moscow` по умолчанию); окна и день должны считаться в этом
  поясе, а не в UTC.

### Как проверить

- `tests/test_schedule_parser.py` — парсер, атомарная запись, сохранение
  старого YAML при ошибке;
- `tests/test_queue_schedule_loading.py` — загрузка при старте, фоновая
  синхронизация, переход недели, битый YAML;
- `queues/tests/test_queue_service.py` — построение занятий, сохранение
  очередей при обновлении, неделя и часовой пояс;
- `tests/test_course_lessons_endpoint.py` — публичный `/lessons`;
- `tests/test_queue_admin_endpoints.py` — админские read-ручки.

## Что пришлось бы изменить, если...

- **...очередь нужно вести одновременно в нескольких аудиториях.** В
  `Lesson`/`QueueRecord` понадобится ключ аудитории и отдельная очередь на
  пару «занятие + аудитория»; `ScheduleProvider` должен возвращать аудиторию
  как часть нормализованного занятия.
- **...backend нужно масштабировать на несколько процессов.** Планировщик
  должен работать в одном выделенном процессе (или под внешней блокировкой),
  а расписание и очереди — читаться из общего хранилища (БД), а не из
  локального YAML/файлов.
- **...понадобятся отмены и дополнительные занятия.** Добавить слой поправок
  перед публикацией `Lesson`: правило «в этот день у этой группы занятия
  нет» и «в этот день и время занятие есть». Формат описать в
  `docs/COURSE_CONFIG.md`, не менять операции очереди.
- **...появится новый вуз.** Добавить провайдер в `ScheduleParser`, формат
  YAML и тесты; `QueueService` не меняется.
- **...потребуется гибкое окно записи.** Вынести `availability(lesson, now)`
  в `ScheduleProvider`/`SchedulePolicy` и заменить ручной `Queue.closed` на
  вычисляемое состояние с учётом ручного открытия преподавателем.
