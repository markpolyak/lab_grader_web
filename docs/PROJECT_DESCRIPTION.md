# Lab Grader Web

## Обзор проекта

**Lab Grader Web** — это автоматизированная веб-платформа для проверки и оценивания лабораторных работ студентов с интеграцией GitHub CI/CD и Google Sheets.

Система позволяет автоматизировать процесс приема и проверки студенческих работ, минимизируя ручной труд преподавателей и обеспечивая объективную оценку через автоматические тесты.

## Назначение

Платформа решает следующие задачи:

- **Регистрация студентов** — связывание ФИО студента с GitHub аккаунтом
- **Автоматическая проверка работ** — валидация кода через GitHub Actions/CI
- **Управление курсами** — поддержка множественных курсов с отдельными настройками
- **Интеграция с Google Sheets** — централизованное хранение данных о студентах и оценках
- **Проверка качества кода** — анализ результатов тестирования и линтинга
- **Антиплагиат** — конфигурация проверки через MOSS (Measure Of Software Similarity)
- **Административная панель** — управление конфигурациями курсов через веб-интерфейс

## Основной функционал

### Для студентов

1. **Выбор курса и группы** — навигация через интуитивный интерфейс
2. **Регистрация** — ввод ФИО и GitHub никнейма с валидацией
3. **Отправка работы на проверку** — автоматический запуск процесса оценивания
4. **Получение результата** — мгновенная обратная связь о статусе проверки

### Для администраторов

1. **Управление курсами** — создание, редактирование, удаление курсов
2. **Редактирование конфигураций** — YAML редактор с подсветкой синтаксиса
3. **Загрузка новых курсов** — импорт конфигураций через веб-интерфейс
4. **Аутентификация** — вход через GitHub; каждый преподаватель видит и меняет только свои курсы (см. «Вход преподавателей и права»)
5. **Массовая проверка лабораторных** — проверка всей группы одной кнопкой (см. «Массовая проверка лабораторной»)

### Процесс проверки работы

1. Студент указывает GitHub-логин, заранее связанный с его ФИО при регистрации
2. Backend проверяет:
   - Наличие логина в столбце `GitHub` листа группы
   - Наличие репозитория `{org}/{github-prefix}-{username}`
   - Наличие `.github/workflows/` (настроен CI)
   - Наличие обязательных файлов (настраивается в конфиге lab: `files: [...]`)
   - Получает последний коммит
   - Валидирует, что студент не модифицировал файл с тестами (`test_main.py`, `tests/`)
   - Получает статусы всех CI проверок (workflows)
   - **Извлекает баллы из логов** (если настроено в конфиге)
3. **Защита от перезаписи**: Результат записывается только если текущее значение ячейки:
   - Пустое
   - Содержит "x" (предыдущая неудачная проверка)
   - Начинается с "?" (пометка преподавателя)
4. Результат записывается в Google Sheets:
   - `v` = успех без баллов
   - `x` = ошибка
   - `v@10.5` = успех с баллами (разделитель зависит от locale таблицы)
   - `v-3` = успех со штрафом
   - `v@10.5-3` = успех с баллами и штрафом
5. Frontend отображает детальный результат проверки с информацией о баллах (персистентно, не всплывающее окно)

### Хранилище конфигураций курсов

Подробности - `docs/COURSE_STORAGE_PLAN.md`, эксплуатация - `docs/DEPLOYMENT.md`.

- Источник выбирается `COURSES_SOURCE`: `local` - каталог `courses/` (разработка, тесты), `github` - приватный репозиторий конфигураций (сервер).
- В режиме `github` каждое сохранение из админки - коммит через Git Data API, автор - GitHub-логин преподавателя. Создание курса (файл + `index.yaml`) - один коммит.
- Чтения обслуживаются из снимка ветки в памяти; новые коммиты подхватываются не реже раза в `COURSES_REFRESH_SECONDS`. Снимок сохраняется на диск, и при недоступном GitHub сервис работает и стартует по нему.
- Редактор хранит версию загруженного файла; сохранение поверх чужой правки - 409, правки остаются в редакторе, можно загрузить актуальную версию.
- До записи проверяются YAML, секции `join` (в том числе запрет уменьшать `join.revision` - и при восстановлении старой версии) и `team`, и то, что преподаватель не убрал себя из `teachers`.
- Под редактором - необязательное поле «Что изменено»: текст становится сообщением коммита (`{course_id}: {текст}`, до 200 символов); пустое поле - `{course_id}: правка через админку`. То же поле есть при восстановлении версии.
- Кнопка «История» у курса: версии (дата, автор, сообщение), просмотр, восстановление с подтверждением.
- Логотипы (`/courses/logos/{name}`) раздаются из хранилища с `ETag`.

### Вход преподавателей и права

Подробности - `docs/MULTI_TEACHER_PLAN.md`.

- **Вход через GitHub.** Кнопка «Войти через GitHub» на `/admin`. Используется тот же OAuth App и тот же callback (`/join/callback`), что и для студентов; назначение входа передаётся в подписанном `state`. Пароли сервис не хранит.
- **Преподаватель курса** - тот, чей GitHub-логин указан в `course.github.teachers` (без учёта регистра). Он видит в админке только свои курсы, включая скрытые и архивные. Пользователь, которого нет ни в одном `teachers` и среди суперадминистраторов, войти не может.
- **Суперадминистратор** - логины из `SUPERADMIN_GITHUB_LOGINS`: доступ ко всем курсам. Исключение логина из переменной действует сразу, без ожидания конца сессии.
- **Аварийный вход** по `ADMIN_LOGIN`/`ADMIN_PASSWORD` (свёрнутый блок на странице входа) - на случай недоступности GitHub; даёт права суперадминистратора.
- **Чужой курс неотличим от несуществующего**: прямой запрос к API чужого курса и к фоновой работе (рассылка, массовая проверка) чужого курса отвечает `404` с тем же телом, что и для несуществующего. Остановить чужую массовую проверку нельзя.
- Права пересчитываются на каждый запрос по текущей конфигурации курса: правка `teachers` действует без повторного входа.
- Преподаватель не может загрузить курс без себя в `teachers` и сохранить курс, удалив себя из `teachers` (`400`). Суперадминистратору можно.
- Сессия - cookie `admin_session` (логин, роль, способ входа; подпись itsdangerous, 1 час). Cookie прежнего формата не принимается: нужно войти заново.

### Рассылка обновлений стартового кода (`propagate-template-update`)

Замена механизма GitHub Classroom «разослать обновление шаблона всем репозиториям студентов». Работает только для лаб с `repo-provisioning: fork` (см. `docs/COURSE_CONFIG.md`) - только в этом режиме репозитории студентов реально являются форками шаблона, и GitHub может построить кросс-репо PR между ними.

- `POST .../propagate-template-update` с `{"dry_run": true}` (по умолчанию) синхронно возвращает сводку по каждому репозиторию, отсортированную по имени. Каждый форк сравнивается с последним коммитом шаблона (по 10 запросов параллельно, ~1,5 с на форк): `needs_update` - в ветке по умолчанию не хватает коммитов шаблона (`commits_behind`), только такие строки можно выбрать для рассылки; `up_to_date` - все коммиты шаблона уже есть, обновлять нечего; `pr_exists` - уже открыт PR, построенный на текущем коммите шаблона; `error` - сравнить не удалось; `not_a_fork` - репозиторий с тем же префиксом не является форком шаблона (обычно созданный до перехода на `fork` или через старый GitHub Classroom).
- Реальный запуск повторяет сравнение для каждого выбранного репозитория: если обновлять нечего, репозиторий получает статус `up_to_date`, и в нём ничего не создаётся - ни служебной ветки, ни PR.
- Сравнение идёт по коммитам, но если коммитов шаблона в ветке по умолчанию нет, дополнительно сверяется содержимое: каждый изменённый шаблоном файл сравнивается по SHA блоба с деревом ветки студента, удалённые файлы должны отсутствовать. Совпало всё - статус `up_to_date` (так распознаётся PR, влитый через «Squash and merge» или «Rebase and merge»: изменения на месте, а исходных коммитов нет). Если проверить нельзя (больше 300 изменённых файлов, дерево репозитория обрезано GitHub) или студент успел ещё раз изменить эти файлы, репозиторий считается нуждающимся в обновлении.
- Повторная рассылка в репозиторий с уже открытым PR передвигает его ветку на новый коммит шаблона и возвращает `pr_updated`; если ветка уже указывала на этот коммит, она не трогается, а статус - `pr_exists`.
- С `{"dry_run": false}` запрос возвращает `202` и `job_id`; рассылка выполняется в фоне (отдельный поток, см. `main._start_background_job`), прогресс опрашивается через `GET /admin/propagate-jobs/{job_id}`. Повторный запуск для той же пары курс/лаба, пока работа выполняется, отклоняется с `409`.
- Открытие PR - это **предложение** изменений, а не принудительный push: слияние остаётся на усмотрение студента (или преподавателя, если у него есть доступ к репозиторию). Автор PR - владелец сервисного `GITHUB_TOKEN`, а не преподаватель лично.
- Репозитории, созданные до переключения лабы на `repo-provisioning: fork`, обновлением не охватываются: они показываются в сводке со статусом `not_a_fork`, задним числом связать их с форк-сетью шаблона нельзя. Причины у этого две и они разные. Созданные через `generate` форками не являются вообще. Созданные в GitHub Classroom - форки, но чужие: GHC сначала делал из репозитория-шаблона преподавателя промежуточный репозиторий механизмом template, а студентам раздавал форки этого промежуточного репозитория. Содержимое совпадает с шаблоном, а родитель - нет, поэтому по той же причине такой репозиторий отвергается и при переходе по ссылке `/join`, с сообщением «Репозиторий с таким именем уже занят».
- Состояние фоновых работ хранится в памяти процесса (`grading/propagate.py`, последние 20 работ). При рестарте бэкенда статус незавершённой работы теряется, но сами уже созданные PR не пропадают - повторный запуск безопасен, для уже открытых PR вернётся статус `pr_exists`. Это требует, чтобы бэкенд запускался **одним uvicorn-воркером** (`CMD` в `backend.Dockerfile` без `--workers`) - при нескольких воркерах опрос статуса работы может попасть в другой процесс и вернуть 404.
- Технически PR открывается не «из шаблона в форк»: GitHub не даёт создать кросс-репо pull request, когда шаблон и репозитории студентов принадлежат одной организации (`head` вида `owner:branch` в этом случае разрешается в сам целевой репозиторий). Вместо этого сервис пользуется тем, что форк и шаблон делят хранилище объектов: в репозиторий студента создаётся служебная ветка `template-update`, указывающая на текущий коммит шаблона, и PR открывается из неё в ветку по умолчанию. При каждой новой рассылке ветка перемещается на актуальный коммит - уже открытый PR при этом обновляется, а не дублируется. Студенту работать с этой веткой не нужно, но она видна в списке веток его репозитория.
- Если обновление меняет файлы в `.github/workflows`, у `GITHUB_TOKEN` должен быть scope `workflow` (для fine-grained токена - разрешение Workflows: Read and write). Без него GitHub отказывается создавать ветку, указывающую на такой коммит, и отвечает `404` - в итогах рассылки это показывается как ошибка с объяснением.
- Прогон CI после мержа PR зависит от `paths`-фильтров workflow конкретной лабы в репозитории-шаблоне - обновление файлов вне этих фильтров не запустит проверку автоматически.

### Массовая проверка лабораторной (`bulk-grade`)

Проверка всей группы одной кнопкой, вместо ожидания, пока каждый студент сам отправит работу. Запускается со страницы лабораторных курса в админке (`/admin/courses/{course_id}/labs`): у каждой лабы есть действие «Заполнить таблицу», в диалоге выбирается группа и, при необходимости, файл с ФИО.

Каждый студент проходит ровно те же проверки, что и при самостоятельной отправке: обязательные файлы, `.github/workflows`, коммиты, запрещённые модификации, результаты CI, номер варианта, баллы из логов, штраф за просрочку. Решение об оценке принимает `grading/bulk.py:evaluate_student` - общая функция для одиночной проверки (`grade_lab`) и массовой, поэтому их поведение не может разойтись.

**Два режима, выбираются полем «Файл с ФИО студента»:**

| Поле | Режим | Что происходит |
|------|-------|----------------|
| заполнено | `by_file` | Перебираются все репозитории организации с префиксом лабы. Из указанного файла берётся первая строка - ФИО студента. По ФИО находится строка в таблице, GitHub-логин из имени репозитория записывается в столбец `GitHub`, затем работа проверяется |
| пусто | `by_sheet` | Проверяются только студенты, у которых GitHub-логин уже указан в таблице |

Подсказки в поле берутся из списка `files` лабы; ключ `student-name-file` (см. `docs/COURSE_CONFIG.md`) предзаполняет его.

**Сопоставление ФИО** - точное после нормализации: схлопывание пробелов (включая неразрывные), регистр, `ё` → `е`. Нечёткий подбор не выполняется намеренно: цена ошибки - оценка, записанная не тому студенту. Репозитории, для которых ФИО не нашлось или нашлось дважды, попадают в отчёт со статусами `unmatched` / `ambiguous` и прочитанным ФИО, чтобы преподаватель исправил вручную.

**Запись GitHub-логина:** пустая ячейка - логин записывается; тот же логин (без учёта регистра) - не перезаписывается; другой логин - `conflict`, строка пропускается целиком и не проверяется ни под одним из логинов.

**Защита оценок:** действует то же правило `can_overwrite_cell`, что и при самостоятельной отправке - перезаписываются только пустые ячейки, `x` и значения, начинающиеся с `?`. Остальные попадают в отчёт со статусом `rejected` и текущим значением. Флага принудительной перезаписи нет.

**Пробный запуск** (`dry_run`) выполняет все проверки и строит полный отчёт, не записывая в таблицу ничего - ни оценок, ни логинов. В отличие от `dry_run` у рассылки шаблона, здесь он тоже фоновая работа: проверки настоящие и занимают столько же времени.

**Технические детали:**

- Запуск возвращает `202` и `job_id`; работа идёт в фоне (отдельный поток, см. `main._start_background_job`), прогресс опрашивается через `GET /admin/bulk-grade-jobs/{job_id}` раз в 2 секунды. Хранилище работ - то же по устройству, что у рассылки шаблона (модульный словарь под блокировкой, не переживает перезапуск). Повторный запуск для той же тройки курс/группа/лаба, пока работа выполняется, отклоняется с `409`; в теле ответа приходит `job_id` идущей работы, и админка подключается к ней вместо того, чтобы показать одну ошибку.
- Строка таблицы считается строкой студента только если в ней есть ФИО. `get_all_values()` отдаёт лист до последней непустой строки, поэтому всё, что лежит под таблицей группы (итог, заметка, случайное число), попадает в тот же столбец GitHub: такая строка показывалась как студент (на живом прогоне - «студент 20»), а при успешной проверке в неё записалась бы оценка. Теперь такие строки попадают в отчёт со статусом `no_name` и не проверяются.
- Отсутствующий репозиторий отличается от репозитория без нужного файла: через API это одно и то же (`file_exists` отвечает `False` в обоих случаях), поэтому проверка существования репозитория делается **только когда что-то уже не сошлось** - в норме лишнего запроса нет. Ошибка называется `REPO_NOT_FOUND` вместо «файл не найден».
- Фоновые работы (и массовая проверка, и рассылка шаблона) запускаются **потоком, а не через `BackgroundTasks` FastAPI**. Задачи `BackgroundTasks` выполняются только после доставки ответа, поэтому оборвавшееся соединение (закрытая вкладка, прокси, сбросивший запрос) оставляло работу зарегистрированной как выполняющуюся, хотя её никто не выполнял, - и лабораторная оставалась занятой до перезапуска бэкенда.
- Работа, которая не доработает до конца, распознаётся двумя способами (`grading/bulk.py:_close_dead_job_locked`), и в обоих случаях помечается `failed` с понятным сообщением, а тройка курс/группа/лаба освобождается - следующий запуск не получит `409`. Уже записанные в таблицу оценки сохраняются: они пишутся батчами по ходу работы.
  - **Нет рабочего потока.** Поток называется `bulk-{job_id}` (`bulk_worker_thread_name`), и его отсутствие через `WORKER_START_GRACE_SECONDS` (30 с) после регистрации означает, что работа не запустилась или её поток умер. Именно так выглядела ошибка на живой контрольной: эндпоинт успевал зарегистрировать работу и падал с 400 на нечисловом ключе лабы.
  - **Поток есть, но молчит** дольше `STALE_JOB_SECONDS` (10 минут). Отметка о признаках жизни обновляется на каждом студенте и на каждом репозитории при обходе организации.
- Если работа зарегистрирована, но запустить её не удалось, эндпоинт освобождает лабораторную сразу (`fail_bulk_job`), не дожидаясь этих проверок.
- Номер лабораторной для запасного способа найти столбец берётся через `optional_lab_number`, а не `parse_lab_id`: **ключ лабы не обязан быть числом** (`quiz` в neural-networks-2026). Номер нужен только лабе без `short-name`; для такой лабы с нечисловым ключом работа падает с понятным сообщением, а не запрос с 400.
- Обращения к Google Sheets идут с таймаутом `SHEETS_TIMEOUT_SECONDS` (30 с, `main.sheets_client()`). Без него gspread ждёт ответа бесконечно, и одно повисшее соединение останавливает всю проверку - та же ошибка для GitHub исправлялась в PR #42.
- Лист читается одним вызовом `get_all_values()`, все поиски (строка студента, столбец лабы, дедлайн, номер варианта) выполняются по сетке в памяти. Поячеечные хелперы тратят ~6 обращений к Sheets API на студента, что для группы из 30 человек выходит за квоту в 60 запросов чтения в минуту.
- Запись - пакетами по 10 ячеек по ходу работы, а не одним блоком в конце: падение, перезапуск или отмена сохраняют уже проставленные оценки.
- Студенты обрабатываются последовательно: GitHub применяет secondary rate limits к всплескам параллельных запросов от одного токена.
- Ошибка на одном студенте (нет коммитов, неверный вариант, недоступный репозиторий) не останавливает работу - она попадает в его строку отчёта. Останавливают работу только общие сбои: нет столбца `GitHub` или столбца лабы, недоступен список репозиториев организации.
- Отмена проверяется между студентами: накопленная порция дописывается в таблицу, работа завершается со статусом `cancelled`.

### Командные лабораторные работы

Лаба, которую студенты выполняют командами: один репозиторий на команду, доступ у всех её участников. Замена group assignment в GitHub Classroom. Ссылка для студентов та же, что и для индивидуальных лаб - `https://<host>/join/{course_id}/{lab_id}`.

**Как перевести лабу в командный режим.** Добавить в конфиг лабы секцию `team` (см. `docs/COURSE_CONFIG.md`); в ней необязательные `size-max` (максимум участников в команде) и `count-max` (максимум команд). Присутствие секции, даже пустой, - и есть признак командной лабы. Остальное как у индивидуальной: обязателен `template-repo`, `repo-provisioning` работает в обоих режимах.

**Что видит студент.** После входа через GitHub - список уже созданных команд лабы: название, описание, логины участников, заполненность («3 из 4») и кнопку «Присоединиться»; плюс форму создания своей команды. Непринявшие приглашение участники помечены отдельно - видно, почему место занято. Повторный переход по той же ссылке приводит участника команды на карточку его команды с ссылкой на репозиторий и кнопкой «Восстановить доступ», которая пересоздаёт протухшее приглашение.

**Как устроены репозитории команд.** `{github-prefix}-team-{N}` в организации курса, приватные; `N` - наименьший свободный номер среди существующих команд лабы. Участники - прямые коллабораторы с правом `push`; владельцы организации и логины из `github.teachers` в состав команды не попадают. Название и описание команды хранятся в поле `description` репозитория в виде `Название — описание` и правятся преподавателем прямо на GitHub. Отдельного хранилища состав команд не имеет: источник истины - сам репозиторий.

**Как удалить студента из команды** (типовая ситуация: студент ошибся при выборе):

1. Открыть репозиторий команды: `https://github.com/{организация}/{github-prefix}-team-{N}`.
2. Settings → Collaborators and teams.
3. Если студент принял приглашение - напротив его логина нажать `Remove`.
4. Если приглашение ещё не принято - оно показано в разделе `Pending invitations`, нажать `Cancel invitation`. Этот шаг обязателен: непринятое приглашение продолжает занимать место в команде и удерживает студента привязанным к ней. Истёкшее приглашение тоже нужно отменять: GitHub не удаляет его сам по истечении 7 дней, и оно занимает место бессрочно. На экране выбора команды такие участники помечены «приглашение истекло».
5. Сообщить студенту, чтобы он снова открыл ссылку `/join/...` - он увидит список команд и сможет выбрать другую.

Коммиты, которые студент успел сделать в старом репозитории, остаются в его истории; при необходимости преподаватель удаляет их обычными средствами Git.

**Как переименовать команду.** Отредактировать `description` репозитория: `Название — описание` (разделитель - пробел, длинное тире, пробел). Если разделителя нет, вся строка показывается студентам как название.

**Как удалить пустую команду.** Удалить репозиторий на GitHub. Номер `N` освободится и будет переиспользован следующей созданной командой.

**Как закрыть создание новых команд.** Выставить `team.count-max` равным текущему числу команд. Вступление в уже созданные неполные команды при этом остаётся доступным: отдельного признака «формирование команд закрыто» нет. Убирать секцию `team` для этого нельзя - лаба перестанет быть командной, и проверка работ перестанет находить репозитории команд.

**Проверка командных работ.** Оценка ставится каждому участнику в его собственную строку таблицы, но репозиторий проверяется один раз на команду: тяжёлая часть (файлы, коммиты, результаты CI, логи job'ов) не повторяется на каждого студента. Защита ячейки (`can_overwrite_cell`) при этом применяется индивидуально - у участника с уже выставленной оценкой она не перезаписывается, остальные оценку получают. Одиночная проверка (студент нажал «Проверить») находит репозиторий его команды по логину и пишет результат только в его строку; студент без команды получает понятное сообщение. В массовой проверке студенты без команды попадают в отчёт со статусом `no_team`, а режим сопоставления по файлу с ФИО для командных лаб недоступен - в репозитории один такой файл на несколько человек.

**Проверка варианта (TASKID) для командных лаб не выполняется:** номер варианта выводится из порядкового номера студента в таблице, у команды такого номера нет. Заданный вместе с `team` ключ `taskid-max` игнорируется, при старте бэкенда это пишется в лог.

**Технические детали и ограничения:**

- Список команд лабы собирается из репозиториев организации (`1 + 2 × число_команд` запросов к GitHub) и кэшируется на 30 секунд: группа из 30 человек, одновременно открывшая страницу, тратит около 21 запроса вместо 630.
- Изменяющие операции (создание команды, вступление) идут под блокировкой своей лабы и внутри неё перечитывают список команд, минуя кэш, - два студента не могут занять один номер, одно название или последнее свободное место. Как и состояние фоновых работ, это корректно только при **одном uvicorn-воркере**.
- Действия преподавателя напрямую на GitHub в момент операции студента блокировкой не охватываются; расхождение исправляется на следующем чтении списка. Лимиты - проверка на момент операции, а не жёсткий инвариант.
- Непринятое приглашение занимает место в команде осознанно: иначе один студент мог бы занять места во всех командах.
- Модерация названий команд не выполняется: текст очищается от управляющих символов и обрезается по длине, за содержание отвечает преподаватель (может отредактировать `description` или удалить репозиторий). Логин создателя команды пишется в лог.
- Личность студента на всех командных эндпоинтах берётся только из подписанной cookie `join_session` (HttpOnly, `SameSite=Lax`, `path=/join`, 30 минут), которую выставляет колбэк OAuth. Из тела запроса, query-параметров и пути логин не принимается никогда.
- Переиспользования состава команд между лабами (аналог «set of teams» в GHC) нет: у каждой лабы свой репозиторий, состав задаётся заново.

### Контрольные работы и секретные ссылки

Контрольная работа - это обычная лаба с двумя дополнительными свойствами: неугадываемой ссылкой и окном доступности. Отдельной сущности «контрольная» в конфиге нет, поэтому проверка работ, штрафы, баллы и антиплагиат работают ровно так же, как у лабораторной. Полное описание - в `docs/SECRET_JOIN_LINKS_PLAN.md`, справочник полей - в `docs/COURSE_CONFIG.md` (секция `join`).

**Зачем.** Обычная ссылка `/join/{course_id}/{lab_id}` отличается от соседней только номером лабы, поэтому её можно угадать перебором и получить репозиторий с заданием заранее. Секретная ссылка выглядит как `https://<host>/j/k7m2q9x4tz` и до публикации не подтверждает даже того, что такая работа существует.

**Как настроить.** В конфиг лабы добавляется секция `join`:

```yaml
labs:
  "7":
    github-prefix: kr1
    short-name: "Тест / КР"
    template-repo: suai-os-2026/kr1-template
    repo-provisioning: fork
    ignore-task-id: true          # вариант генерируется в репозитории студента
    join:
      link: secret
      opens-at: "2026-10-15 10:00"
      closes-at: "2026-10-15 11:30"
      revision: 1
```

Время указывается в часовом поясе курса (`timezone`). **Время открытия нужно указывать явно**: дата без времени, как и дедлайн в таблице, означает конец дня.

**Как получить ссылку.** Собрать её руками нельзя - токен вычисляется сервером из `SECRET_KEY` и конфига. Два способа, оба показывают одну и ту же строку:

1. **Админка** (основной): страница `/admin/courses/{course_id}/labs`, столбец «Ссылка для студентов» - ссылка целиком и кнопка копирования. Столбец общий для всех работ: у обычной лабы там `/join/{course_id}/{lab_id}`, у работы с секретной ссылкой - `/j/{token}`, а состояние окна («откроется 15.10.2026 10:00») и напоминание про отзыв показываются только там, где они есть. Работа без `template-repo` ссылки не имеет. Ссылка доступна с момента появления лабы в конфиге, задолго до открытия: рассылку можно подготовить заранее.
2. **Скрипт** на сервере или локально: `python scripts/join-link.py --course os-2026 --lab 7`.

**Что происходит по времени.**

| Момент | Ссылка `/j/{token}` | Список работ студента | Проверка работ |
|---|---|---|---|
| до `opens-at` | «работа ещё не открыта», со временем открытия | не показывается | публичная - как у несуществующей работы; массовая из админки работает |
| `opens-at` … `closes-at` | создаёт репозиторий, чинит доступ | показывается | обе работают |
| после `closes-at` | новые репозитории не создаются, доступ к уже созданному чинится | показывается | обе работают |

Работа остаётся видимой и после закрытия приёма: сдают её как раз тогда.

**Как отозвать ссылку.** Увеличить `join.revision` в конфиге курса. Старая ссылка перестаёт работать немедленно, новую нужно взять в админке и раздать заново. Уменьшать `revision` нельзя - сохранение такого конфига через админку отклоняется, иначе отозванная ссылка ожила бы. Ссылка также отзывается сменой `SECRET_KEY` - **все сразу**, поэтому менять ключ во время контрольной нельзя (`docs/DEPLOYMENT.md`).

**Чего секретная ссылка не скрывает.** Конфиги курсов лежат в публичном репозитории проекта, поэтому сам факт существования контрольной, её `github-prefix` и имя шаблона видны на GitHub. Секретен ранний доступ к заданию: содержимое защищено приватностью репозитория-шаблона, а ссылка - тем, что её нельзя угадать.

**Ограничения.**

- Окно задаётся на лабу целиком, поэтому модель верна, пока все группы пишут работу одновременно. Если группы будут писать в разное время, пересылка ссылки между ними станет дырой.
- Командная лаба (секция `team`) с секретной ссылкой пока не поддерживается: такое сочетание - ошибка конфигурации, она пишется в лог при старте, а запрос к лабе отвечает понятной ошибкой.
- Ссылка общая для всех студентов: персональных и одноразовых ссылок нет.
- Переименование курса или смена ключа лабы меняют ссылку. Если это возможно, задайте явный `join.id` - тогда ссылка переживёт переименование.

### Квизы на лекции

Короткий квиз в конце лекции: студенты отвечают с телефонов, присутствие и баллы сами попадают в Google-таблицу курса. Подробности - `docs/QUIZ_PLAN.md`.

**Подготовка.**

1. Банк вопросов - markdown-файл в формате `quiz_questions.md` из `course-maker`: заголовок `###` - вопрос (число с `%` в конце - вес), строка `**Вариант А:** …` - вариант вопроса, четыре пункта списка `- ` - ответы, правильный помечен ` ✓` в конце. В тексте можно использовать код и формулы (`$…$`, `$$…$$`). Курсивная строка сразу под заголовком вопроса видна только преподавателю. Все вопросы - выбор одного из четырёх.
2. В листах групп Google-таблицы добавьте столбец квиза: короткое имя (например `К5`) во второй строке, как у лабораторных.
3. Админка → курс → «Лабораторные работы» → «Квизы» → выберите файл, укажите название, столбец, балл за квиз и время на вопрос (по умолчанию 20 с) → «Загрузить». Ошибки формата перечисляются все сразу («Вопрос 1.2, Вариант Б: 5 вариантов ответа (нужно 4)»). Файл сохраняется в хранилище конфигураций (`quizzes/<курс>/<квиз>.md`), параметры - в его заголовке.

**Изменение параметров.** Кнопка «Изменить» в списке квизов: название, столбец в таблице, балл, секунд на вопрос, секунд на показ ответа, разные варианты. Вопросы не меняются (чтобы заменить вопросы - удалите квиз и загрузите файл заново). Уже открытый запуск работает со старыми параметрами - отмените его и запустите снова. Одновременная правка с другого устройства даёт конфликт, а не молчаливую перезапись.

**Проведение.** «Запустить» открывает экран проектора с QR-кодом. Студент сканирует код; первый раз входит через GitHub (вход действует 180 дней), дальше QR-код сразу ведёт в ожидание. Логин ищется в листах групп таблицы - кого там нет, получает отказ со ссылкой на регистрацию. «Начать» - вопрос уходит на телефоны всем одновременно; варианты ответа у каждого студента перемешаны; время считает сервер. По истечении времени (или по кнопке «Завершить вопрос», если все уже ответили) проектор показывает правильный ответ и распределение ответов; ответы после этого не принимаются. Через «секунд на показ ответа» (по умолчанию 10, параметр квиза) следующий вопрос запускается сам, после последнего - итоги; отсчёт виден на проекторе и телефонах. «Дальше» - перейти сразу, «Пауза» - остаться на ответе (например, чтобы его разобрать), дальше - по кнопке. 0 секунд на показ ответа - переход только по кнопке. Если у вопроса несколько вариантов (А/Б), все получают один и тот же, выбранный случайно при запуске. «Завершить» и «Отменить» доступны всё время; на курс - один идущий квиз.

**Рейтинг.** Галочка «Показывать рейтинг» при запуске (по умолчанию включена). В лобби на экране - GitHub-логины подключившихся (последние 30). После каждого вопроса, на экране с правильным ответом, - топ-5 и кто быстрее всех ответил верно на этот вопрос; на итоговом экране - топ-10. Порядок один и тот же на каждом шаге: сначала баллы (те же, что пишутся в таблицу), при равенстве - меньше суммарное время на верные ответы (от начала вопроса до ответа). Итоговый рейтинг - это положение после последнего вопроса; на баллы в таблице скорость не влияет. В топе - только набравшие больше нуля. Каждый студент видит на телефоне своё место («Вы на 7-м месте из 42»).

На экран выводятся только GitHub-логины, никогда ФИО из таблицы. Переключатель «Не показывать мой логин в рейтинге на экране» на телефоне скрывает логин (место в рейтинге сохраняется, на экране - «участник скрыт»); выбор запоминается на телефоне для следующих квизов.

**Баллы.** Балл за вопрос - `балл за квиз × вес / сумма весов` (если веса указаны не у всех вопросов - поровну). Подключился и ничего не набрал - `0`, не подключался - ячейка пустая. После завершения баллы записываются в столбец квиза листа группы каждого участника, только в пустые ячейки; занятые ячейки и листы без столбца показываются в итоге, запись можно повторить.

**Квиз как отметка посещаемости.** Столбец квиза ищется только во второй строке листа группы (в первой - дедлайны лабораторных, тоже даты). Если посещаемость ведётся по столбцу на лекцию с датой во второй строке, укажите в поле «Столбец в таблице» дату лекции (например `12.11.2026`). Даты сравниваются по значению: `12.11.2026` найдёт и столбец, где формат ячейки показывает только `12.11` (Google API отдаёт дату так, как она отображается в ячейке, а не как в строке формул): баллы лягут в столбец этой лекции, присутствовавший с нулём верных ответов получит `0`, отсутствовавший - пустую ячейку. Стоимость посещения задаётся баллом за квиз, итоговая формула таблицы просто суммирует столбцы. Если дата введена не так, как в таблице, экран проектора ещё до начала покажет предупреждение «в листах … нет столбца». Для контрольной заведите отдельный столбец (например `КР1`) и отдельный квиз.

**Контрольная: разные варианты разным студентам.** Отметьте при загрузке «Разные варианты вопроса разным студентам» (в файле - `variants-per-student: true`). Тогда каждый студент получает свой вариант каждого вопроса (`**Вариант А:**`, `**Вариант Б:**`, … в файле) - сосед с другим вариантом не подскажет. Вариант закреплён за студентом и не меняется при переподключении; вопрос с единственным вариантом все получают одинаковым. Ответ проверяется по варианту студента. Проектор не показывает текст такого вопроса (общего нет) - только номер и сколько ответили, а после показа ответа - сколько верных по каждому варианту. Журнал ответов записывает вариант каждого студента. Без отметки все получают один вариант, выбранный при запуске (обычный квиз).

**Перезапуск backend во время квиза.** Состояние квиза живёт в памяти, но каждое событие (открытие, подключение, вопрос, ответ, показ, завершение, запись) сразу дописывается в журнал `logs/quiz/<курс>/<run_id>.jsonl`. При старте backend восстанавливает по журналам квизы последних суток: незавершённый продолжается с того же вопроса (если время вопроса истекло во время перезапуска - показывается ответ), принятые ответы сохраняются, завершённый, но не записанный в таблицу - записывается. Телефоны и проектор переподключаются сами; ответ, отправленный в секунды перезапуска, студент отправляет повторно. Квиз хранит текст вопросов на момент запуска, так что правка файла квиза восстановлению не мешает.

**Режим «Только в аудитории».** Галочка при запуске квиза («Запустить» → «Только в аудитории»), по умолчанию выключена - на контрольной и в других случаях пересылка QR-кода не мешает. Режим защищает от участия вне аудитории:

- текст вопроса показывается только на экране в аудитории; на телефоне - номер вопроса, отсчёт и варианты ответа, у каждого студента в своём порядке (подсмотреть у соседа «он нажал второй» бесполезно);
- QR-код на экране меняется каждые 15 секунд, код из ссылки действует 15-30 секунд: ссылка, пересланная в чат группы, быстро перестаёт работать. Студент, открывший актуальный QR-код, получает пропуск на 10 минут - его хватает на вход через GitHub;
- новые участники подключаются только до конца первого вопроса; уже подключившиеся переподключаются в любой момент;
- на проекторе варианты ответа появляются только при показе правильного ответа, вместе с распределением.

Полностью исключить участие вне аудитории нельзя: товарищ в аудитории может сфотографировать экран и переслать. Режим делает это хлопотным - на каждом вопросе и за отведённые секунды. Несовместим с «разными вариантами»: на экране один общий вопрос.

**Ограничения.** Без режима «Только в аудитории» защиты от участия вне аудитории нет. Нагрузку проверяет `scripts/quiz-load-test.py`.

### Файл описания курса

Каждый курс описывается в отдельном YAML файле со следующей структурой:

```yaml
course:

  github:
    organization: "os-course-2025"
```

### Извлечение баллов из логов CI

Система поддерживает автоматическое извлечение баллов из логов GitHub Actions для записи в Google Sheets. Эта функция полностью опциональна и активируется добавлением секции `score` в конфигурацию лабораторной работы.

#### Конфигурация

```yaml
labs:
  "1":
    github-prefix: "task1"
    short-name: "ЛР1"
    score:                        # Опциональная секция
      patterns:                   # Список regex паттернов (пробуются по порядку)
        - 'ИТОГО:\s*(\d+(?:[.,]\d+)?)\s*баллов'           # "ИТОГО: 100 баллов" -> 100
        - 'ОЦЕНКА.*?ЖУРНАЛ:\s*(\d+(?:[.,]\d+)?)'         # "ОЦЕНКА В ЖУРНАЛ: 10.0" -> 10.0
        - '##\[notice\]Points\s+(\d+(?:[.,]\d+)?)/\d+'   # "##[notice]Points 10/10" -> 10
        - 'Score\s+is\s+(\d+(?:[.,]\d+)?)'               # "Score is 10.5" -> 10.5
```

#### Правила работы

1. **Множественные паттерны**: Паттерны пробуются по порядку. Используется первый найденный результат.

2. **Первая capturing group**: Паттерн должен содержать захватывающую группу `(...)` — это значение будет извлечено как балл.

3. **Разделители**: Система принимает оба разделителя (`10.5` и `10,5`) во входных данных.

4. **Валидация**: Если балл найден в нескольких джобах, все значения должны совпадать. Иначе — ошибка.

5. **Обязательность**:
   - Если `score.patterns` **указан** → баллы **обязательны**. Если не найдены — ошибка.
   - Если `score.patterns` **не указан** → баллы не ищутся (backward compatible).

6. **Автоматический разделитель**: При записи в Google Sheets используется разделитель из locale таблицы:
   - `ru_RU`, `de_DE`, `fr_FR` → запятая (`10,5`)
   - `en_US`, `en_GB` → точка (`10.5`)

#### Формат записи в таблицу

| Ситуация | Формат записи | Пример |
|----------|--------------|---------|
| Только успех | `v` | `v` |
| Успех с баллами | `v@{score}` | `v@10.5` или `v@10,5` |
| Успех со штрафом | `v-{penalty}` | `v-3` |
| Успех с баллами и штрафом | `v@{score}-{penalty}` | `v@10.5-3` |
| Неудача | `x` | `x` |

#### Примеры паттернов для разных форматов

**Русский формат:**
```yaml
score:
  patterns:
    - 'ИТОГО:\s*(\d+(?:[.,]\d+)?)\s*баллов'
    - 'ПРЕДВАРИТЕЛЬНАЯ.*?ОЦЕНКА.*?ЖУРНАЛ:\s*(\d+(?:[.,]\d+)?)'
```

**GitHub Actions notice:**
```yaml
score:
  patterns:
    - '##\[notice\]Points\s+(\d+(?:[.,]\d+)?)/\d+'
```

**Autograding format:**
```yaml
score:
  patterns:
    - 'Score\s+is\s+(\d+(?:[.,]\d+)?)'
    - 'Total:\s+(\d+(?:[.,]\d+)?)'
```

#### Советы по созданию паттернов

1. **Используйте одинарные кавычки** в YAML для regex (`'...'`), чтобы избежать двойного экранирования.

2. **Гибкие паттерны**: Используйте `.*?` для пропуска переменного количества символов:
   ```yaml
   - 'ПРЕДВАРИТЕЛЬНАЯ.*?ОЦЕНКА.*?ЖУРНАЛ:\s*(\d+(?:[.,]\d+)?)'
   ```

3. **Учитывайте пробелы**: После таймстемпа в логах могут быть дополнительные пробелы. Используйте `\s*` или `\s+`.

4. **Тестируйте паттерны**: Используйте [regex101.com](https://regex101.com/) для проверки паттернов на реальных логах.

#### Отображение на frontend

При успешном извлечении баллов, информация отображается в результатах проверки:

```
✅ Результат CI: Все проверки пройдены (Баллы: 10.5)
Результат: v@10.5
Баллы: 10.5
```

#### Техническая реализация

- **Модуль**: `grading/score.py`
- **Функция извлечения**: `extract_score_from_logs(logs, patterns)`
- **Определение разделителя**: `get_decimal_separator(spreadsheet)`
- **Форматирование**: `format_grade_with_score(base, score, penalty, separator)`

### GitHub API
- Проверка существования пользователей
- Проверка существования репозиториев
- Получение содержимого файлов
- Получение информации о коммитах
- Получение статусов CI/CD проверок (check runs)

### Google Sheets API
- Чтение списка студентов
- Чтение GitHub никнеймов
- Запись результатов проверок
- Обновление данных о регистрации

**Конфигурация столбцов:**
- `student-name-column`: Номер столбца с ФИО студентов (0-based индексация: 0=A, 1=B, 2=C)
- `lab-column-offset`: Смещение между столбцом студента и первой лабораторной работой
- Примечание: В коде автоматически добавляется +1 для совместимости с gspread (1-based индексация)

### MOSS (Антиплагиат)
- Конфигурация языка программирования
- Настройка максимального количества совпадений
- Интеграция для проверки оригинальности кода

## Развертывание

### Локальная разработка

Пошаговая настройка (своя таблица, service account, GitHub-организация,
OAuth App, конфигурация курса) — в [`docs/DEVELOPMENT.md`](DEVELOPMENT.md).

```bash
docker compose up --build
# Frontend: http://localhost:8080, backend: http://localhost:8000
```

### Production

Проект использует GitHub Actions для автоматической сборки и публикации Docker образов:

```yaml
# Образы публикуются в GitHub Container Registry
ghcr.io/markpolyak/lab_grader_web-frontend:latest
ghcr.io/markpolyak/lab_grader_web-backend:latest
```

### Переменные окружения

Необходимо создать файл `.env` со следующими переменными:

```bash
# GitHub
GITHUB_TOKEN=ghp_...

# Аварийный вход в админку (права суперадминистратора)
ADMIN_LOGIN=admin
ADMIN_PASSWORD=secure_password

# GitHub-логины суперадминистраторов через запятую: доступ ко всем курсам
SUPERADMIN_GITHUB_LOGINS=

# Security
SECRET_KEY=random_secret_key_for_signing_cookies

# Публичный адрес сервиса: из него собирается секретная ссылка /j/{token},
# которую админка показывает преподавателю
PUBLIC_BASE_URL=https://labgrader.example.ru

# Адреса обратного прокси, которым можно доверять X-Forwarded-For.
# Пусто - не доверять никому (см. docs/DEPLOYMENT.md)
FORWARDED_ALLOW_IPS=

# Путь к ключу Google service account (по умолчанию credentials.json)
CREDENTIALS_FILE=/app/google-credentials/credentials.json

# Вход через GitHub: студенты (/join/..., командные работы) и преподаватели
# (админка). Без них эти эндпоинты отвечают 503, в админку - только аварийный
# вход. См. docs/REPO_GENERATION_PLAN.md, docs/MULTI_TEACHER_PLAN.md
GITHUB_OAUTH_CLIENT_ID=
GITHUB_OAUTH_CLIENT_SECRET=
FRONTEND_URL=http://localhost:8080
```

Полный список с комментариями — в `.env.example`.

## Безопасность

- **Аутентификация** — cookie-based сессии с криптографическим подписыванием (itsdangerous)
- **Таймаут сессий** — автоматический выход через 1 час
- **Unprivileged контейнеры** — Docker образы работают от непривилегированного пользователя
- **Multi-stage builds** — минимизация поверхности атаки и размера образов
- **.dockerignore / .gitignore** — исключение чувствительных данных из репозитория
- **Валидация входных данных** — проверка всех пользовательских вводов
- **Защита от модификации тестов** — проверка целостности файла test_main.py

## Тестирование

### Запуск

`main.py` при импорте требует переменные окружения; тестам достаточно
фиктивных значений, в Google и GitHub они не ходят:

```bash
ADMIN_LOGIN=test ADMIN_PASSWORD=test SECRET_KEY=test GITHUB_TOKEN=dummy pytest tests/ -v
ADMIN_LOGIN=test ADMIN_PASSWORD=test SECRET_KEY=test GITHUB_TOKEN=dummy pytest tests/ --cov=. --cov-report=term-missing
cd frontend/courses-front && npm test
```

### Что покрыто

| Файл | Что проверяет |
|---|---|
| `test_grade_lab_characterization.py` | Эндпоинт проверки работы целиком: успех, провал CI, ошибки репозитория, защита тестов, окно доступности |
| `test_grader.py`, `test_ci_checker.py` | Оркестратор проверки и разбор результатов CI |
| `test_github_client.py`, `test_sheets_client.py` | Клиенты GitHub и Google Sheets |
| `test_penalty.py`, `test_score.py`, `test_taskid.py` | Штрафы, баллы из логов, номер варианта |
| `test_lab_column_lookup.py`, `test_lab_resolution.py` | Поиск столбца лабораторной, разрешение `lab_id` в конфигурацию |
| `test_bulk_grading.py` | Массовая проверка |
| `test_join_endpoints.py`, `test_repo_provisioning.py` | Создание репозиториев студентов через `/join` |
| `test_join_links.py` | Секретные ссылки и окна доступности |
| `test_teams.py` | Командные лабораторные |
| `test_propagate.py` | Рассылка обновлений шаблона |
| `test_admin_endpoints.py` | Авторизация административных маршрутов (`require_admin`) |
| `test_rate_limit.py` | Ограничение частоты запросов |

### CI/CD

Тесты (pytest) запускаются GitHub Actions (`.github/workflows/tests.yml`) на каждый push и на pull request в `main` и `hackathon/**`.
