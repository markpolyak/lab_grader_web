# План разработки: хранилище конфигураций курсов с версионированием

Требования и план реализации фичи. Опирается на `docs/MULTI_TEACHER_PLAN.md` (автор изменения — `AdminIdentity.login`) и выполняет требования §13 `docs/SECRET_JOIN_LINKS_PLAN.md`.

## 1. Постановка задачи

Конфигурации курсов лежат в `courses/` репозитория backend: копируются в образ (`backend.Dockerfile`), на сервере подменяются смонтированным каталогом (`docker-compose.example.yaml`), правятся то через админку, то руками на сервере, то коммитом в репозиторий. Последствия:

- правка через админку живёт только на диске сервера: истории нет, кто и что поменял — неизвестно, при пересоздании volume правка теряется;
- одновременная правка двумя преподавателями молча затирает одну из них;
- конфигурации с ID таблиц, организациями и сроками лежат в публичном репозитории.

Нужно:

- конфигурации вне репозитория backend, в приватном хранилище;
- каждое сохранение из админки — версия с автором и временем;
- просмотр истории и восстановление версии из админки;
- конкурирующие правки не теряются молча;
- локальная разработка и тесты работают без доступа к приватному хранилищу.

## 2. Как устроено сейчас

Все обращения к конфигурациям — в `main.py` и `grading/course_index.py`:

| Место | Что делает |
|---|---|
| `load_course_index()` | читает `courses/index.yaml` |
| `iter_course_configs()` → `grading.course_index.iter_course_configs` | перебор курсов индекса, единственная точка перечисления (`SECRET_JOIN_LINKS_PLAN.md` §6, §13) |
| `validate_course_index()` | при старте: сверка индекса с файлами каталога (`os.listdir`), разбор каждого курса |
| `get_course_by_id()` | индекс + файл курса, `_meta` из индекса |
| `DELETE /courses/{id}` | ставит `status: hidden` и перезаписывает `index.yaml` |
| `GET/PUT /courses/{id}/edit` | читает файл; сохраняет после `_validate_join_sections` через `_write_file_atomically` |
| `POST /courses/upload` | пишет файл курса и дописывает `index.yaml` (два независимых действия) |
| `StaticFiles` на `/courses/logos` | раздаёт `courses/logos/` |
| `scripts/join-link.py` | `grading.course_index.iter_course_configs` без сервера |
| `check_token_collisions(...)` | при старте, по `iter_course_configs()` |

Файлы читаются на каждый запрос, кеша нет.

## 3. Архитектурное решение

### 3.1. Хранилище — приватный GitHub-репозиторий

Отдельный приватный репозиторий (например, `markpolyak/lab_grader_courses`) — источник истины:

```
index.yaml
<course>.yaml
logos/<file>
quizzes/<course_id>/<quiz_id>.md     # зарезервировано: docs/QUIZ_PLAN.md
```

- Каждое сохранение — коммит. Committer — владелец токена сервиса, author — GitHub-логин преподавателя (`{login}@users.noreply.github.com`). История, diff и восстановление — средствами git.
- Отдельный fine-grained токен `COURSES_GITHUB_TOKEN` с единственным правом Contents: read/write на этот репозиторий. Основной `GITHUB_TOKEN` (доступ к организациям курсов) для конфигураций не используется.
- Прямые коммиты в репозиторий конфигураций (с компьютера преподавателя) остаются допустимыми: сервис подхватывает их при обновлении снимка (§5.2).

### 3.2. Подключаемый источник

Слой хранилища с двумя реализациями, выбор — `COURSES_SOURCE`:

- `local` (по умолчанию) — каталог `courses/`, поведение как сейчас; для разработки (`docs/DEVELOPMENT.md`) и тестов;
- `github` — репозиторий из §3.1; для сервера.

### 3.3. Отклонённые варианты

- **Локальный git-репозиторий на volume сервера.** Нужен git в образе, бэкап volume и всё равно push во внешний репозиторий; два источника истины.
- **База данных с таблицей версий.** История, diff и восстановление пишутся с нуля; появляется сервис, которого в проекте нет.
- **Contents API (`PUT /repos/{r}/contents/{path}`) для записи.** Один файл на коммит, а создание курса меняет два файла (курс и `index.yaml`). Git Data API покрывает и одно-, и многофайловую запись одним механизмом (§5.3).

## 4. Интерфейс хранилища

Новый модуль `grading/course_store.py`:

```python
@dataclass(frozen=True)
class StoredFile:
    path: str
    content: bytes
    version: str          # github: blob sha; local: sha256 содержимого

@dataclass(frozen=True)
class Revision:
    sha: str
    date: datetime
    author: str           # GitHub-логин или имя автора коммита
    message: str

class CourseStore(Protocol):
    def read(self, path: str) -> StoredFile | None: ...
    def list(self, prefix: str = "") -> list[str]: ...
    def write(self, changes: dict[str, bytes | None], expected: dict[str, str | None],
              message: str, author: str) -> None: ...
    def history(self, path: str, limit: int = 30) -> list[Revision]: ...
    def read_at(self, path: str, sha: str) -> StoredFile | None: ...
    @property
    def supports_history(self) -> bool: ...
```

- `changes`: путь → новое содержимое, `None` — удалить.
- `expected`: путь → версия, которую видел автор изменения (`None` — файла не должно существовать). Несовпадение хотя бы одной — `StoreConflictError`, ничего не записано.
- `StoreUnavailableError` — хранилище недоступно для записи.
- `grading/course_index.py` перестаёт открывать файлы сам: `load_course_index(store)`, `read_course_file(store, entry)`, `iter_course_configs(store)`.
- `get_course_store()` в `main.py` создаёт хранилище по окружению один раз при старте.

## 5. Реализации

### 5.1. `LocalCourseStore`

- Чтение с диска на каждый вызов, как сейчас (правка файла в редакторе действует сразу).
- `write`: проверка `expected` по sha256 текущего содержимого, затем каждый файл через `_write_file_atomically`; файл курса пишется раньше `index.yaml`. Многофайловая запись не атомарна — для разработки допустимо.
- `history`/`read_at` не поддерживаются (`supports_history = False`); админка скрывает историю.

### 5.2. `GitHubCourseStore`: чтение

- В памяти — **снимок** ветки (`COURSES_GITHUB_BRANCH`, по умолчанию `main`): sha коммита, дерево `path → blob sha`, содержимое блобов. Все чтения сервиса обслуживаются из снимка.
- Обновление: не чаще раза в `COURSES_REFRESH_SECONDS` (по умолчанию 30) — `GET /repos/{r}/git/ref/heads/{branch}` с `If-None-Match`; при новом sha — `GET /repos/{r}/git/trees/{sha}?recursive=1`, недостающие блобы — `GET /repos/{r}/git/blobs/{sha}` (по sha блоба содержимое неизменно, кеш вечный). Обновление выполняется по запросу, обратившемуся к хранилищу после истечения интервала, под блокировкой; остальные запросы в это время получают текущий снимок.
- После каждого успешного обновления снимок сохраняется на диск (`COURSES_CACHE_DIR`). При старте, если GitHub недоступен, сервис поднимается со снимка с диска и пишет предупреждение; если нет ни GitHub, ни снимка — старт прерывается с понятной ошибкой (как сейчас при невалидном индексе).
- Недоступность GitHub во время работы: чтения продолжаются по последнему снимку, ошибка журналируется не чаще раза в интервал обновления.

### 5.3. `GitHubCourseStore`: запись

1. Обновить снимок (принудительно, без ожидания интервала).
2. Сверить `expected` с blob sha файлов в снимке; несовпадение — `StoreConflictError`.
3. `POST /git/blobs` для новых файлов → `POST /git/trees` (`base_tree` — дерево текущего коммита; удаление — элемент с `sha: null`) → `POST /git/commits` (`parents` — текущий коммит, `author` — преподаватель) → `PATCH /git/refs/heads/{branch}` с `force: false`.
4. Ссылку обогнали (ответ 422 на шаге 3) — повторить с шага 1 один раз: если изменения касались других файлов, проверка `expected` пройдёт; если тех же — `StoreConflictError`.
5. Успех — снимок обновляется сразу, без ожидания интервала.
6. Сетевые ошибки и 5xx — `StoreUnavailableError`.

`history(path)` — `GET /repos/{r}/commits?path={path}&sha={branch}&per_page={limit}`; `read_at(path, sha)` — `GET /repos/{r}/contents/{path}?ref={sha}`.

## 6. Проверка до записи

Общая функция `validate_course_change(course_id, new_text, old_data, identity)` — для сохранения, загрузки и восстановления:

1. YAML разбирается, есть ключ `course` (сейчас — только при загрузке);
2. `_validate_join_sections` (включая запрет уменьшать `join.revision`, требование §13 `SECRET_JOIN_LINKS_PLAN.md` — восстановление старой версии тоже его проходит);
3. разбор секций `team` (`parse_team_config`) — ошибка блокирует сохранение, а не только пишется в журнал при старте;
4. преподаватель не удаляет себя из `teachers` (`MULTI_TEACHER_PLAN.md` §7.2).

Для изменений индекса — уникальность `id` и существование файлов, на которые ссылается индекс (то, что сейчас делает `validate_course_index` при старте).

## 7. Эндпоинты

### 7.1. Изменения в существующих

| Маршрут | Изменение |
|---|---|
| `GET /courses/{id}/edit` | ответ дополняется `version` файла курса |
| `PUT /courses/{id}/edit` | принимает `version`; `StoreConflictError` → 409 «Конфигурацию курса изменил другой пользователь. Скопируйте свои правки и обновите страницу»; `StoreUnavailableError` → 503 «Хранилище конфигураций недоступно, изменения не сохранены» |
| `POST /courses/upload` | файл курса и строка в `index.yaml` — одной записью (`expected`: файла нет, индекс в текущей версии) |
| `DELETE /courses/{id}` | скрытие курса — запись `index.yaml` через хранилище |
| `/courses/logos/{name}` | `StaticFiles` заменяется маршрутом, читающим `logos/{name}` из хранилища; `Content-Type` по расширению, `ETag` — версия файла, `Cache-Control: public, max-age=3600` |

Сообщения коммитов: `{course_id}: правка через админку`, `{course_id}: новый курс`, `{course_id}: курс скрыт`, `{course_id}: восстановлена версия {sha[:7]}`.

## 8. Перечисление курсов и производные данные

- `iter_course_configs()` и `get_course_by_id()` читают из хранилища; для `github` — из снимка в памяти, без сетевых запросов на пути студента.
- `check_token_collisions` выполняется при старте и после каждого обновления снимка, давшего новый коммит; коллизия — запись в журнал, как сейчас.
- `validate_course_index` при старте проверяет снимок/каталог через хранилище, без `os.listdir`.
- `scripts/join-link.py` использует `COURSES_SOURCE` и переменные §9: по умолчанию `local`.

## 9. Окружение

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `COURSES_SOURCE` | `local` | `local` или `github` |
| `COURSES_GITHUB_REPO` | — | `owner/name` репозитория конфигураций |
| `COURSES_GITHUB_BRANCH` | `main` | ветка |
| `COURSES_GITHUB_TOKEN` | — | fine-grained токен, Contents: read/write только на этот репозиторий |
| `COURSES_REFRESH_SECONDS` | `30` | интервал проверки новых коммитов |
| `COURSES_CACHE_DIR` | `/app/courses-cache` | снимок на диске для старта без GitHub (volume) |

При `COURSES_SOURCE=github` без репозитория или токена старт прерывается с понятной ошибкой.

## 10. Переход

1. Создать приватный репозиторий и перенести `courses/` с историей: `git filter-repo --subdirectory-filter courses` в копии репозитория backend, затем push.
2. На сервере задать переменные §9, volume для `COURSES_CACHE_DIR`; убрать монтирование `./courses` из `docker-compose.example.yaml`, обновить `docs/DEPLOYMENT.md` (раздел о добавлении курса и логотипа).
3. Проверить, какие тесты читают реальные файлы `courses/` (`test_admin_endpoints.py`, `test_lab_resolution.py`, `test_rate_limit.py`), перевести их на фикстуры (временный каталог с `LocalCourseStore`).
4. В репозитории backend оставить в `courses/` пример курса для `docs/DEVELOPMENT.md` и тестов; реальные конфигурации удалить из него отдельным коммитом после проверки на сервере. История публичного репозитория не переписывается.

## 11. Frontend

- Редактор курса (`components/course-list`, режим `isAdmin`): хранит `version` из `GET .../edit` и отправляет его в `PUT`; на 409 — диалог с текстом ошибки, правки остаются в редакторе (можно скопировать), кнопка «Загрузить актуальную версию».
- Панель «История» у курса (если `GET .../history` не 404): список версий (дата, автор, сообщение), просмотр версии только для чтения, кнопка «Восстановить эту версию» с подтверждением.
- На 503 — сообщение о недоступности хранилища, правки остаются в редакторе.
- Переводы ru/en/zh.

## 12. Не входит в объём

- Сравнение версий (diff) в админке — ссылка на коммит в GitHub достаточна.
- Ревью изменений (PR) перед применением.
- Загрузка логотипов через админку.
- Правка полей `index.yaml` из админки, кроме скрытия курса.
- Вебхук GitHub для мгновенного подхвата внешних коммитов — интервал §5.2 достаточен.

## 13. Тесты

Новый файл `tests/test_course_store.py` (GitHub API — через `responses`, уже в `requirements-dev.txt`):

- `LocalCourseStore`: чтение, запись, конфликт по `expected`, удаление, `supports_history = False`;
- `GitHubCourseStore`, чтение: построение снимка из ref/tree/blobs; 304 на ref не вызывает загрузку дерева; новые коммиты подхватываются после интервала; блобы не загружаются повторно;
- старт: GitHub недоступен + снимок на диске — сервис стартует; нет ни того, ни другого — понятная ошибка;
- запись: один файл, два файла одним коммитом (одна последовательность blobs → tree → commit → ref), удаление, `author` — переданный логин; `expected` не совпал — `StoreConflictError` без запросов на запись; ref обогнали изменением другого файла — успешный повтор; того же файла — конфликт; 5xx — `StoreUnavailableError`;
- `history` и `read_at`.

Дополнения к существующим файлам:

- `tests/test_admin_endpoints.py`: `PUT .../edit` с устаревшей `version` — 409, файл не изменён; загрузка курса — файл и индекс в одной записи; восстановление версии с меньшим `join.revision` — 400; история и восстановление для чужого курса — 404;
- маршрут логотипов: содержимое, `Content-Type`, `ETag`;
- существующие тесты проходят с `LocalCourseStore` на фикстурах.
