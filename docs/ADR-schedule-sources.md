# ADR: Нормализация расписаний в YAML и подключение источников

- **Команда:** lab_grader_web (участники решения не указаны)
- **Статус:** принято (фиксирует текущую архитектуру и её ограничения)
- **Дата:** 2026-11-08

## Контекст

Очередь защиты должна знать расписание группы, часовой пояс, временное окно
открытия и закрытия очереди, а также лабораторные работы, разрешённые в каждом
занятии. Расписание хранится по курсу в `schedules/<course_id>.yaml`; пример
структуры есть в [schedules/dev-course.yaml](../schedules/dev-course.yaml).
Файл содержит слоты, повторения по дням и чётности недель, разовые изменения
(`corrections`) и настройки очереди.

Расписание читает backend при проверке активного и следующего занятия. В
[grading/queue/schedule_window.py](../grading/queue/schedule_window.py) источник
слотов разбирается из YAML, а сеансы вычисляются на запрошенную дату и
кэшируются в памяти процесса с ключом, включающим время изменения файла.
Проверка активного занятия предшествует обращению к Google Sheets: лист
очереди создаётся/открывается только при наличии активного занятия
([main.py](../main.py), `queue_status`). Администратор может просматривать и
редактировать YAML, получать список групп и запускать обновление расписания
([main.py](../main.py), `/admin/courses/{course_id}/schedule/...`).

В коде уже есть контракт [ScheduleSource](../grading/schedule/base.py) с
нормализованным объектом `ScheduledSession`, а также декоратор и реестр в
[grading/schedule/registry.py](../grading/schedule/registry.py). Текущий поток,
однако, использует эти части не как универсальную фабрику:

1. `parse_schedule_file` в [grading/schedule/__init__.py](../grading/schedule/__init__.py)
   проверяет конфигурацию и создаёт `ManualScheduleSource` для каждой группы,
   независимо от значения `source`.
2. `ManualScheduleSource` в [grading/schedule/manual.py](../grading/schedule/manual.py)
   преобразует сохранённые YAML-слоты, повторы и коррекции в
   `ScheduledSession`.
3. Обновление через `refresh_all_groups` в том же модуле напрямую создаёт
   `GuapScheduleSource`. Этот адаптер получает занятия из локального снимка
   `data/schedule.json` через vendored `suai-schedule-parser`, затем переводит
   их в формат `slots` в YAML ([grading/schedule/guap.py](../grading/schedule/guap.py)).
   Учитель может вручную править слоты и коррекции через админский редактор.
4. Импортированные слоты не перечитываются из GUAP при каждом запросе
   очереди: нормализованный YAML является источником истины для чтения.

Список групп для админского обновления объединяет `manual-groups` из YAML и
числовые листы Google Sheets, кроме информационного листа. Если таблицу
прочитать не удалось, endpoint возвращает предупреждение, но оставляет ручные
группы доступными. Ошибка при обновлении одной группы не мешает обновить
остальные; результаты и ошибки возвращаются по группам.

Данные расписания должны переживать перезапуск backend и оставаться доступными
при обработке следующих запросов. YAML хранит конфигурацию и ручные изменения;
кэш слотов и источников — только ускоряющий, процессный. В текущем Docker
Compose корень проекта примонтирован в `/app`, но образ
[backend.Dockerfile](../backend.Dockerfile) сам по себе не копирует `schedules/`
и `data/`: при другом способе запуска эти данные нужно предоставить отдельно.

Обновление файлов расписания выполняется атомарной заменой временного файла,
но межпроцессной блокировки или транзакционного хранилища нет. Вызов
`GuapScheduleSource._ensure_snapshot` запускает загрузку снимка только если
`data/schedule.json` отсутствует; существующий снимок endpoint не обновляет.
Поэтому вызов «обновить расписание» не гарантирует получение актуального
снимка GUAP, если файл уже лежит на диске.

## Рассмотренные варианты

### Вариант 1: Импортировать источники в нормализованный YAML (выбранный)

Адаптер читает внешний источник по административному запросу и преобразует
данные в общую структуру `slots`. Backend далее разбирает YAML одним
`ManualScheduleSource`; расписание для очереди не зависит от доступности
внешнего сервиса во время занятия. Этот вариант соответствует текущему
потоку GUAP и ручному редактированию.

- **Плюсы:**
  - Сохранены предсказуемые повторения, часовые пояса, разрешённые лабораторные
    и точечные коррекции.
  - Источник не вызывается на каждом просмотре или изменении очереди.
  - Коррекции и настройки очереди хранятся рядом с импортированными слотами;
    текущий refresh сохраняет их при замене списка слотов.
- **Минусы:**
  - Между обновлением расписания и импортом внешний источник может измениться.
  - Нужны правила идентификаторов слотов, сопоставления групп и сохранения
    преподавательских правок: refresh заменяет `slots`, поэтому правки самих
    импортированных слотов не переживают обновление.
  - Сейчас универсальная диспетчеризация обновления ещё не реализована:
    `refresh_all_groups` привязан к GUAP.
- **Что потребует от проекта:** Для нового импорта — адаптер и тесты; для
  универсального подключения — выбирать реализацию по `source` вместо прямого
  создания `GuapScheduleSource`, сохраняя атомарную запись YAML. Новые
  зависимости и миграция базы данных не нужны, если формат `slots` достаточен.

### Вариант 2: Читать расписание внешнего источника непосредственно при запросе

При проверке очереди backend вызывает API или парсер расписания и строит
сеансы из свежих данных. Можно добавить кэш на несколько минут, но он не
устраняет зависимость от сети и источника в момент обращения.

- **Плюсы:**
  - Изменения внешнего расписания могут быть видны без отдельного импорта.
  - Не требуется синхронизировать отдельную копию расписания вручную.
- **Минусы:**
  - Недоступность или задержка внешнего сервиса непосредственно влияет на
    регистрацию в очереди.
  - Нужно решать кэширование, квоты, повторные запросы и поведение при
    временных сбоях; поведение может отличаться между запросами.
  - Учительские коррекции и дополнительные сведения, которых нет во внешнем
    источнике, всё равно требуют отдельного слоя хранения.
- **Что потребует от проекта:** Доступ к внешним API во время работы очереди,
  обработку сетевых ошибок/лимитов и явную политику кэширования; вероятно,
  новые настройки и зависимости для каждого источника.

### Вариант 3: Полностью подключаемые runtime-источники через реестр

Каждая реализация `ScheduleSource` самостоятельно возвращает
`ScheduledSession`; конфигурация выбирает её через `source`, а общая фабрика
создаёт нужную реализацию и для чтения, и для обновления. YAML может остаться
слоем настроек и коррекций или использоваться только для ручного источника.

- **Плюсы:**
  - Единый контракт и явное разделение интеграций с университетскими
    системами.
  - Для источников с подходящими API возможна работа без копирования
    расписания в YAML.
- **Минусы:**
  - Один контракт должен учитывать различные возможности источников:
    загрузку, коррекции, идентификаторы групп и правила обновления.
  - Если источник вызывается при чтении, сохраняются риски доступности и
    квот варианта 2; если данные кешируются, снова появляется задача
    сохранения и обновления снимка.
  - Нынешний реестр не подключён к фабрике чтения, а endpoint обновления
    напрямую использует GUAP, поэтому одной регистрации класса недостаточно.
- **Что потребует от проекта:** Переделать фабрику в
  `parse_schedule_file`, обработку конфигурации и диспетчеризацию обновления;
  определить жизненный цикл runtime-источника, ошибки и правила совмещения
  данных. При выборе внешних runtime API могут понадобиться новые зависимости
  и переменные окружения.

## Решение

Сохранять расписание очереди в едином нормализованном YAML-файле на курс и
использовать этот файл для чтения сеансов. Внешние расписания импортировать
адаптерами в структуру `slots`, сохраняя ручные коррекции и настройки. Это
оставляет проверку окна очереди быстрой и независимой от сети, сохраняет
текущее администрирование расписания и не вводит новое хранилище.

Реализованный GUAP-путь — пример импорта, но текущая абстракция источников
подключена не полностью. Реестр нужен для регистрации адаптеров, однако:

1. Чтобы добавить источник, преобразующий данные во `slots`, добавить модуль
   адаптера и тесты преобразования; зарегистрировать модуль импортом в
   `grading/schedule/__init__.py`, если нужна регистрация; затем подключить его
   к `refresh_all_groups` (сейчас функция вызывает GUAP напрямую).
2. Если источник должен непосредственно выдавать сеансы, также изменить
   `parse_schedule_file` и фабрику чтения: сейчас эта функция всегда строит
   `ManualScheduleSource`, а не выбирает класс из реестра.
3. В любом случае преобразовывать исходные данные в контракт
   `ScheduledSession` и явно определить часовой пояс, стабильный `slot_id`,
   границы временного окна и смысл `allowed_lab_ids` (`None` — все лабораторные,
   пустой список — закрытый слот).
4. Проверить работу с `corrections`, ручным редактором YAML, частичными
   ошибками обновления и отсутствием необязательных метаданных источника.

Регистрация нового класса через `@register_source` сама по себе не переключает
ни чтение, ни административное обновление расписания.

## Последствия

### Что становится проще

- Проверка активного занятия и следующего сеанса опирается на локальную
  конфигурацию и не требует вызова внешнего сервиса на каждый запрос.
- Расписание можно проверить и скорректировать как один YAML-файл; отдельная
  запись для состояния очереди в базе данных не нужна.
- Ошибка одного внешнего источника при импорте видна администратору и не
  блокирует успешное обновление других групп.

### Что становится сложнее или невозможным

- Свежесть импортированных данных зависит от явного импорта, а не от внешнего
  расписания в реальном времени.
- Новый источник нельзя полноценно подключить одним файлом: сегодня требуется
  изменить точку чтения и/или обновления в зависимости от его роли.
- Если снимок GUAP уже существует в `data/schedule.json`, текущий
  `refresh-all` повторно не загружает его; актуализацию снимка нужно решить
  отдельно, прежде чем полагаться на это действие как на принудительную
  синхронизацию.

### Известные ограничения и риски

- **Перезапуск backend во время занятия:** сеансы повторно вычисляются из
  расписания YAML, поэтому теряются только процессные кэши. Если YAML или
  необходимые конфигурационные файлы не попали в рабочую директорию/том,
  расписание недоступно; для снимка GUAP отсутствие файла вызывает попытку
  загрузки, которая может завершиться ошибкой.
- **Несколько процессов backend:** каждый процесс держит собственный кэш.
  Ключ учитывает `mtime` расписания, поэтому после изменения общего файла
  каждый процесс должен перечитать его; при файловой системе с ненадёжным
  обновлением `mtime` возможен устаревший кэш. Общая блокировка и синхронизация
  между процессами не реализованы.
- **Одновременное изменение одного расписания:** атомарная замена защищает
  читателей от частично записанного YAML, но два администратора или два
  обновления могут перезаписать изменения друг друга; победит последняя
  запись. Принята для текущего режима администрирования, но не гарантирует
  сохранность параллельных правок.
- **Google Sheets недоступен или достигнута квота:** получение перечня групп
  возвращает предупреждение и использует ручные группы, если они настроены.
  Ошибка отражается в ответе административного endpoint.
- **GUAP/парсер недоступен или группа отсутствует:** обновление конкретной
  группы возвращает ошибку, а результаты других групп сохраняются. Старые
  слоты проблемной группы остаются в YAML. Снимок на диске автоматически
  обновляется только когда отсутствует; устаревший существующий снимок может
  успешно дать устаревшее расписание.
- **Данные не сохранены между развёртываниями:** Compose примонтирует корень
  проекта, но образ backend отдельно не копирует `schedules/` и `data/`.
  Другой способ развёртывания должен предоставить постоянные/актуальные
  расписания и снимки как файлы или тома.
- **Обновление после ручной правки слота:** успешный импорт заменяет весь
  список `slots` группы. Правки полей импортированных слотов могут быть
  потеряны; исключения, добавленные как `corrections`, и `queue_settings`
  сохраняются. Ручные группы с `source: manual` обновлением пропускаются.

## Что пришлось бы изменить, если...

- **...очередь нужно вести одновременно в нескольких аудиториях:** добавить
  идентификатор аудитории к ключу слота и всем точкам выбора/проверки очереди;
  текущая модель различает курс, группу и занятие, но не аудиторию как
  отдельное измерение.
- **...backend нужно масштабировать на несколько процессов:** заменить
  локальную синхронизацию/кэши и незащищённые обновления YAML на общее хранилище
  с блокировками или версионированием. Все процессы должны видеть одно
  расписание, а конкурентные изменения — обнаруживаться или сериализоваться.
- **...появился новый университетский портал:** написать и протестировать
  преобразование данных в общий формат, затем добавить его в диспетчеризацию
  импорта. Для runtime-чтения дополнительно подключить источник в фабрике
  `parse_schedule_file`; одного декоратора `@register_source` недостаточно.
- **...требуется гарантированное расписание «на сейчас» из GUAP:** изменить
  обновление снимка так, чтобы оно действительно загружало новую версию даже
  при существующем `data/schedule.json`, и определить безопасное поведение при
  неудачной загрузке.
