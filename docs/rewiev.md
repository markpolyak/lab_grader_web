## Приоритетные находки

### 🔴 Высокий приоритет

#### 1. Регистрация позволяет закрепить чужой GitHub-аккаунт

Публичный обработчик проверяет существование введённого GitHub-пользователя,
но не подтверждает, что посетитель управляет этим аккаунтом. Если для найденного
ФИО логин ещё не записан в таблице, backend сохраняет введённое имя и выдаёт
подписанную сессию для этой пары. Queue-endpoints затем доверяют этой сессии.

**Риск:** подмена студенческой идентичности и запись в очередь от имени другого
существующего GitHub-пользователя.

См. [регистрацию](../main.py), [создание сессии](../main.py) и
[проверку сессии очереди](../main.py).

#### 2. Для командной лабораторной пропускается проверка CI

`queue_register` запускает `ensure_ci_passed` только для индивидуальной работы.
Для team lab проверка пропускается, и сервер всё равно может добавить команду
в очередь. Frontend также не использует поле `can_register` из ответа статуса
для блокировки кнопки.

**Риск:** команда может попасть в очередь без подтверждённого успешного CI.

См. [регистрацию в очередь](../main.py) и
[QueueSection.jsx](../frontend/courses-front/src/components/registration-form/QueueSection.jsx).

#### 3. Очередь может не открыться в чистом Docker-развёртывании

Backend ищет YAML расписания в `schedules/`, но [backend.Dockerfile](../backend.Dockerfile)
не копирует этот каталог в образ, а [docker-compose.example.yaml](../docker-compose.example.yaml)
не монтирует его как volume. В результате в чистом контейнере расписание групп
может отсутствовать; без расписания queue не находит активные занятия.
Изменения расписания внутри контейнера также не сохранятся после его замены.

**Риск:** очередь не открывается по расписанию либо конфигурация теряется при
пересоздании контейнера.

#### 4. При отсутствии `SECRET_KEY` используется известный ключ

В [main.py](../main.py) задан fallback `super-secret-key`, который используется
для подписи сессий. Если переменная окружения не задана или задана пустой,
подписи создаются известным ключом.

**Риск:** подделка подписанных сессий при небезопасной конфигурации.
Фактические настройки deployment не проверялись.

### 🟠 Средний / высокий приоритет

#### 5. Apps Script не включается по описанному сценарию; блокировка не общая

`closeDay()` прекращает работу, если в `autoclose_status` нет
`script_enabled=TRUE`. Поиск по текущему коду не обнаружил backend- или
frontend-механизма, который записывает этот флаг, хотя документация описывает
переключатель в интерфейсе. Установка триггера сама по себе поэтому не
разрешает скрипту закрывать листы.

Также Apps Script использует `copy_lease`, но backend эту аренду не читает и
не записывает: его блокировка действует только внутри процесса. Если обе
стороны всё же запустить одновременно, возможны гонки при копировании и
удалении листа.

**Риск:** автоматическое закрытие не работает либо backend и скрипт одновременно
обрабатывают один лист.

См. [Code.gs](../queue-apps-script/Code.gs),
[locks.py](../grading/queue/locks.py) и
[инструкцию установки](SETUP.md).

## Исправление, подтверждённое в обновлении

- **Чётность GUAP теперь сохраняется.** Экспорт различает недели `all`, `odd`
  и `even`, а одинаковые пары разных недель больше не схлопываются в одну
  запись. См. [guap.py](../grading/schedule/guap.py).
- **Парсер поставляется в Docker-образе.** Это устраняет прежнюю проблему
  отсутствующего vendor-парсера, но не проблему отсутствующего каталога
  `schedules/`.

## Исправление, внесённое после аудита

- **Snapshot сохраняет повторные регистрации.** Backend и Apps Script теперь
  считают строки по мультимножеству `(дата, группа, ФИО, лаба, пара)`: одинаковые
  регистрации не схлопываются, а уже скопированная часть корректно пропускается
  при повторном запуске. Позиция не используется как идентификатор, поскольку
  она может переиспользоваться или меняться при перенумерации.
- Добавлен backend-тест на повторную регистрацию с теми же данными, включая
  переиспользованную позицию.
